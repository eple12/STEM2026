# FORMULA-AI Racer — 프로토타입 (사람 운전, Phase A)

STEM2026 축전용 3D 레이싱 게임. 현재 단계 = **사람이 직접 운전하는 플레이 가능 프로토타입**.
AI는 아직 없음 (퀄리티 확인 후 도입). 전체 기획은 [CONCEPT.md](CONCEPT.md).

## 자주 쓰는 명령

저장소 루트(`STEM2026/`)의 PowerShell/cmd 기준.

**Kaggle 학습 → 배포 파이프라인** (한 서킷 전체를 알아서 돌림)

```bat
ai_sw_gpu\kaggle\train_track.bat Monza
ai_sw_gpu\kaggle\train_track.bat Monza Monza_v26k_retry
```

`[서킷] [체크포인트 이름(생략 시 <서킷>_v26k)]`. 순서: CPU/GPU parity 검사 → 커널 push →
2분마다 상태 확인(끝날 때까지 창은 그냥 둬도 됨) → 체크포인트 fetch → trace로 랩타임 측정 →
`_best`/`_bestwide` 중 배포할 걸 선택(`assets/policies/<서킷>.npz`를 **덮어쓰기 전에 항상 물어봄**) →
배포했으면 **그 서킷 퀄리파잉 고스트를 다시 찍을지 물어봄** → 체크포인트는 `ai_sw/policy/<서킷>/`,
로그는 `ai_sw/logs/<서킷>/`로 정리. 배포하면 `ai_sw/policy/RECORDS.md`도 자동 갱신.
**터미널이 죽었거나 창을 닫았는데 커널은 Kaggle에서 계속 돌고 있을 때** — 푸시 없이 다시 붙음
(parity·푸시 건너뛰고 폴링부터 이어서 fetch → trace → 배포 질문 → 정리):

```bat
ai_sw_gpu\kaggle\train_track.bat --attach Melbourne Melbourne_v26_best
```

`OUT_NAME`은 처음 푸시할 때 쓴 이름 그대로여야 함(커널 이름이 여기서 나옴). 커널이 아직 RUNNING이든
이미 COMPLETE든 상관없음.

**`_bestlap.npz`** (2026-09-20~): 학습 중 어떤 eval이든 **가장 빠른 완전 클린 랩**(오프트랙 0)을 낸 시점의 가중치.
`_best`/`_bestwide`는 (등급, 도달 거리) 기준이라 "T1이지만 빠른 클린 랩"을 놓치는데(Melbourne 95.5초가 그렇게 사라짐),
이건 랩 타임 기준으로 따로 저장함. `train_track.bat`의 배포 선택지 `[3]`, 로그의 `*BESTLAP*` 표시.
eval 로그의 `lap` 값과 `trace_rl`의 best lap은 이제 엄격한 클린(허용치 0) 기준임.

**서킷 하나만 램프/추가 옵션을 바꿔서 돌릴 때**(3번째 인자가 기본 레시피 플래그를 *통째로 대체*하므로 필요한 걸 다 적어야 함):

```bat
ai_sw_gpu\kaggle\train_track.bat MexicoCity MexicoCity_v26_ramp20 "--ddqn --line-k 0 --stop-after-stale 600 --eval-backlog 1 --n-step 6 --stop-if-no-perfect 900 --off-ramp-end 2.0"
```

`--off-ramp-end X`는 오프트랙 비용 램프의 끝 배율만 덮어씀(기본 1.6, 도달 시점은 그대로).
eval 로그의 `off-track@0.15:3,0.30:12r1`은 `출발위치:오프트랙 스텝 수`(`rN`=복구 횟수).

자세한 레시피/실험 기록은 [ai_sw_gpu/kaggle/README.md](../ai_sw_gpu/kaggle/README.md).

**퀄리파잉 고스트 녹화** (AI의 가장 빠른 PERFECT 랩 → `assets/ghosts/<서킷>.npz`)

```bat
.venv312\Scripts\python.exe ai_sw\tools\record_ghost.py --circuit Monza
.venv312\Scripts\python.exe ai_sw\tools\record_ghost.py --all
.venv312\Scripts\python.exe ai_sw\tools\record_ghost.py --circuit Spa --laps 8 --keep-faster
```

`--all`은 학습된 정책이 있는 서킷 전부, `--laps`는 달릴 플라잉 랩 수(기본 5),
`--keep-faster`는 기존 고스트보다 빠를 때만 덮어씀.
`--attempts N`은 best-of-N: 0번 시도는 정지 출발, 나머지는 결승선 150~500m 앞에서 굴러 들어가는 시도
(`--attempt-laps` 랩씩)이고, **결승선 통과 상태가 정상 플라잉 랩에서 도달 가능한 랩만** 후보로 인정해 그중
가장 빠른 클린 랩을 저장함(통과 속도 ≤ 정지 출발 랩의 최고 통과 속도+0.5%, 횡위치 ±0.25m, 방향각 +0.02rad;
`--start-speed-tol`, `--start-lat-tol`). 굴러 들어가는 시도의 첫 통과는 보통 부정하게 빠르므로 버려지고
두 번째 랩부터 쓰임(Melbourne: 정지 출발 96.72초 → 96.54초).
`--dry-run`은 저장 없이 결과만 출력. 기본값(`--attempts 1`)은 예전과 같은 정지 출발 → `--laps 5`개 플라잉 랩이고, `train_track.bat`의 고스트 질문도 이 기본값으로 실행함. 정책을 교체했으면 고스트도 다시 찍어야
퀄리파잉 상대가 새 정책과 맞음(위 파이프라인이 끝에 물어봄).

**게임 실행 / 체크포인트 확인**

```bat
ai_sw\run.bat
cd ai_sw && ..\.venv312\Scripts\python.exe -m tools.trace_rl --circuit Monza --policy assets\policies\Monza.npz --out ..\trace.png
```

`trace_rl`은 `ai_sw/`에서 `-m tools.trace_rl`로 돌려야 import가 맞음(`train_track.bat`도 그렇게 호출).

## UI — F1 중계 스타일

브랜드 요소(빨강 #E10600, 근사 블랙, 15° 기울기 도형, 자간 넓은 대문자)는 `game/ui.py`
한 곳에 있고 **시작 메뉴와 주행 중 HUD가 같이 씀** — 두 화면이 따로 놀지 않게.

### 시작 메뉴 (`game/menu.py`)

두 화면이다. **메인 메뉴**(`ModeMenu`)는 A/D 또는 ←→로 퀄리파잉/그랑프리 카드를 고르고
ENTER, ESC 종료. **서킷 선택**(`StartMenu`)은 W/S 또는 ↑↓, ENTER 시작, ESC는 메인 메뉴로.
서킷 패널 우상단에 세션 정보가 뜬다 — 퀄리파잉이면 그 서킷의 고스트 랩 타임(없으면
`NO GHOST LAP · SOLO RUNS`), 그랑프리면 랩 수. 레이스에서 나오면 방금 달린 세션의 서킷
선택으로 돌아온다.

**서체**: F1 공식 서체(Formula1)는 상용이고 그 원형인 **Titillium Web**은 SIL OFL임.
저장소에는 아무 폰트도 넣지 않고(Windows 기본 폰트는 재배포 대상이 아님),
`pick_font()`가 이 순서로 찾음:

1. `assets/fonts/` 의 `Formula1-Bold.ttf` / `TitilliumWeb-Bold.ttf` — **여기에 넣으면 자동 적용**
2. Windows 기본 `bahnschrift.ttf` (DIN 계열 콘덴스드, 현재 사용 중) → `seguisb` → `tahoma`
3. 없으면 Ursina 기본 폰트

찾은 서체는 `Text.default_font`로 지정해서 **HUD까지 같은 서체**로 통일됨.

**형태**: 배경은 직사각형, 각진 평행사변형은 강조 요소(선택 행, 빨간 액센트)에만 씀 —
실제 중계 그래픽이 그렇고, 전부 기울이면 화면이 불안해 보임. `skew_quad()`는 기울기를
**높이에서 유도**함(고정 오프셋이면 0.05 높이 행에 맞춘 값이 0.7 높이 패널을 쐐기로 만듦).

> 삽질 기록: 처음엔 평행사변형이 **전부 안 보였음**. 꼭짓점을 읽는 순서(좌상→우상→우하)로
> 나열하면 화면상 시계방향 = **뒷면**이라 컬링됨. 차 그림자가 사라졌던 것과 완전히 같은 원인.

**서킷 정보**는 실제 주행하는 지오메트리에서 뽑음 — 표시되는 거리가 실제 랩 거리
(Spa 7.004 km, Monza 5.793 km로 실측과 일치). 코너 수는 곡률에서 유도한 값이라
공식 수치와 ±2 차이날 수 있음(Monza 10 vs 공식 11, Austin 20 vs 20).

### 주행 중 HUD (`game/hud.py`, `game/hudkit.py`)

2025 시즌 **F1 TV 중계 그래픽**을 바탕으로 함. (F1 로고·Formula1 서체는 상표/상용이라 쓰지
않고, 로고 자리에 직접 그린 `F-AI` 마크(`game/logo.py`), 서체는 Bahnschrift의
Regular/SemiBold/Bold 인스턴스를 씀.)

**로고**는 글자가 아니라 도형임 — 모든 변이 같은 각도로 기울고, 빨간 F의 윗팔이 마크 전체 위로
길게 뻗어 그 아래 흰 AI를 덮는 한 덩어리. Pillow로 4배 크기에 그려 줄인 뒤 텍스처 쿼드로 붙이므로
(UI 레이어에는 안티에일리어싱이 없음) 대각선이 매끄럽고, 폰트를 안 써서 어느 PC에서나 같음.
결과/일시정지 카드의 빨간 타일에는 같은 마크를 흰색 단색으로 씀.

| 위치 | 내용 |
|---|---|
| 좌상 | **타이밍 타워** — 헤더(워드마크 + `LAP 2/3`, 퀄리파잉은 세션 시계), 행마다 순위 · 팀 컬러 마크 · TLA · 인터벌. P1 순위 칸은 빨강, 내 행은 밝게, 페널티는 타워 오른쪽 앰버 태그 |
| 하단 중앙 | **텔레메트리** (크게) — 레브 LED 15개, 속도(고정 피치 숫자), 기어 박스, 스로틀/브레이크 바, TC/ESP/AIDS OFF/SLIP 태그 |
| 우하 | **드라이버 크롬** — 흰 순위 칸 + 이름, 진행 중 랩타임(중계처럼 0.1초 단위), 목표 시간(퀄리파잉은 AI 기록, 레이스는 베스트 랩), 퀄리파잉 델타 태그, 섹터 바 3개 |
| 좌하 | 트랙 맵(점만) |
| 상단 중앙 | 출발 신호 — 5열 × 2등(중계 그래픽과 같은 형태), 경고/페널티는 **RACE CONTROL** 박스 |

속도·기어·페달은 시선이 이미 가 있는 차 바로 아래 가운데에, 랩타임은 오른쪽 구석에 둠.

타이밍 색은 실제 중계 규칙 그대로 — 보라 = 세션 베스트, 초록 = 자기 베스트, 노랑 = 자기
베스트보다 느림. 랩을 마치는 순간 크롬이 그 랩타임을 3초간 해당 색으로 **전체 자릿수**로
보여줌(중계에서 결승선 통과 때 고정되는 것과 같음).

**그리는 방식이 핵심.** 예전 HUD는 Ursina `Text`/`Entity` 약 200개였고, A/B로 재보니
**그리는 데만 프레임당 약 4 ms**(Panda 컬/드로우, 노드·상태 변경 비용)였음 — 아래 HDR
후처리 전체보다 비쌌음. `hudkit`은 같은 오버레이를 몇 개의 메시로 그림:

* `ShapeLayer` — 모든 판·바·램프·점을 버텍스 버퍼 하나에. 색/위치/크기 변경은 numpy 사본을
  고치고 프레임당 최대 한 번 업로드.
* `TextLayer` — 모든 라벨을 서체(굵기)당 Geom 하나로. 글리프 쿼드는 `DynamicTextFont`의
  글리프 페이지에서 직접 잘라 씀. 라벨마다 고정 슬롯이 있고 글자가 바뀌면 그 슬롯만 다시 씀.
  `mono=True`면 숫자를 고정 피치로 그려 속도·시간이 숨쉬듯 흔들리지 않음.

인레이스 HUD 전체가 드로우콜 6~7개. 결과적으로 **후처리·실사 셰이딩을 넣고도 프레임이 더 빠름**
(아래 "그래픽" 절의 표).

> 삽질 2건. ① Bahnschrift는 가변 폰트라 굵기마다 파일이 없음 — FreeType 페이스 인덱스의
> 상위 16비트가 명명 인스턴스 번호(1 Light … 3 Regular, 4 SemiBold, 5 Bold). 바운딩 박스로는
> 구분이 안 돼서 글리프 페이지의 잉크 양을 재서 확정함. ② 빌드 중에 숨긴 도형이 다시 보였음 —
> 도형을 추가할 때마다 목록에서 버퍼를 다시 이어 붙여서, 먼저 숨겨 둔(정점을 한 점으로 접은)
> 도형이 원상복구됐음. 이제 라이브 버퍼에 append만 함.

## 그래픽 — 실사 렌더링 (2026-10)

목표는 "인디게임"이 아니라 F1 게임·그란투리스모 계열의 화면. **물리는 한 줄도 건드리지 않았고**
(vehicle/surface/trackdata/AI 무변경, config의 물리 상수 무변경), 바뀐 건 렌더링뿐.
전후 비교는 `tools/preview_scene.py`로 찍음(아래).

| 요소 | 무엇을 | 어디 |
|---|---|---|
| **HDR 카메라 체인** | 씬을 R11G11B10 float 버퍼(2x MSAA, 창이 크면 렌더 스케일 — 아래 성능 2)에 그린 뒤 한 패스로 현상: 밉맵 블룸, ACES 톤매핑, 그레이드(스플릿 톤·대비·채도), 비네트, 그레인, 고속에서 화면 가장자리 방사 블러 | `post.py` |

### 성능 2 — 20대 그랑프리, 1080p 전체화면 80+ fps (2026-10-04)

20대 그랑프리에서 1080p 전체화면이 51 fps, 1600×900 창이 43 fps였다. `tools/perf_gp.py`로
실제 게임 루프를 돌리며 Python과 Panda의 컬·드로우를 나누고(`--parts`, `--cprofile`), PStats
(`--pstats`, `text-stats.exe`로 스레드별·GPU 타이머)를 보고, 노트북 온도 때문에 실행마다 10~30%
흔들리는 걸 피하려고 **한 실행 안에서 120프레임마다 번갈아** 재는 A/B(`--ab trees|cars|hud|aniso`,
`--ab-pixels N`)로 항목별 값을 매겼다.

| 바꾼 것 | 효과 |
|---|---|
| **렌더 파이프라인 스레드화** (`RENDER_THREADING = "Cull/Draw"`) | 컬과 드로우가 다음 프레임의 Python과 겹쳐 돔. 1600×900: 23.0 → 17.1 ms |
| **Ursina 프레임 루프 교체** (`game/frameloop.py`) | Ursina는 매 프레임 엔티티 ~350개를 전부 돌며 `enabled`·부모 체인·`update` 유무를 확인함 — 게임 자체 업데이트보다 비쌌음. 할 일 있는 엔티티만 돌게 바꿈. 기본 셰이더의 `camera_world_position`을 엔티티 ~30개에 매 프레임 새로 넣던 것(새 RenderState → Panda 상태 GC 1.2 ms)도 공유 배열 하나로 |
| **마우스 피킹 끔** | 키보드 게임인데 매 프레임 UI·월드에 레이캐스트하고 전체 엔티티의 hover를 지웠음(~0.75 ms) |
| **4x → 2x MSAA** | 스레드화 후 GPU가 병목이 됨. 4x 3.2 ms, 2x 0.6 ms |
| **렌더 스케일** (`RENDER_MAX_PIXELS`) | 3D 장면을 이 픽셀 수까지만 그리고 후처리에서 창 크기로 늘림(+약한 샤프닝), HUD는 항상 창 해상도. 1280×720로 두면 1080p가 91–99 fps였지만 화면이 덜 선명해서 **지금은 0(끔, 항상 원래 해상도)** — 1080p 전체화면 ~17 ms(59 fps), 1280×720 창 ~10 ms(100 fps). 1600×900(=1440000)이면 그 사이 |
| **나무 아틀라스 이방성 4x → 1x** | 나무 비용 전부(1080p에서 1.3 ms)가 이것이었음. 나무는 카메라를 향한 세로 카드라 차이가 안 보임 |
| **차 그림자 맵 2048 → 1024**, PCF 4×4 → 3×3 | 차 한 대 그리는 데 GPU 1.8 ms였음 |
| 블룸 밉 4단 → 3단 | 같은 범위, 1080p에서 ~0.4 ms |
| 평평한 서킷에서 노면 높이 조회 생략 (`Track.is_flat`) | f1tenth 서킷은 높이·뱅크가 전부 0인데 매 프레임 100여 점의 최근접 샘플을 찾았음 |
| 미니맵 점 20개를 배열 한 번에 (`hudkit.ShapeBatch`) | 점마다 move·show 40번 → 1번 |
| 세션 빌드 후 `gc.freeze()` | 가끔 10~20 ms 걸리던 전체 GC가 세션 내내 사는 객체를 안 훑게 |

결과(Monza 레벨 6, 20대, 1랩째 혼전 포함 30초, 같은 노트북 Iris Xe):

| | 전 | 후 |
|---|---|---|
| 1920×1080 전체화면 | 19.5 ms (51 fps) | **10.1–11.0 ms (91–99 fps)**, p95 12.4–13.2 ms — 렌더 스케일 켰을 때. 지금 기본(원래 해상도)은 ~17 ms (59 fps) |
| 1600×900 | 23.0 ms (43 fps) | **~10.7 ms (93 fps)** |
| 1280×720 (기본 창) | — | **8.9 ms (113 fps)**, p95 11.0 ms |

p95가 12 ms를 넘는 건 1랩째 첫 시케인처럼 20대가 한 화면에 몰릴 때다. 잘라 본 것 중 효과가
없던 것: 나무 셰이더 단순화(스페큘러·하늘 반사 제거, 유지는 함), 나무를 불투명 다음에 앞에서부터
그리기(유지), 나머지 텍스처의 이방성, HUD(GPU 타이머엔 1.2 ms로 나왔지만 A/B로는 0).

```bash
../.venv312/Scripts/python.exe tools/perf_gp.py --size 1920 1080 --parts
```

> **스레드화의 함정: 그림자가 차보다 한 프레임 늦었다.** 그림자 맵 조회 행렬을 Python에서 계산해
> 공유 배열(PTA)에 써 넣었는데, 배열은 파이프라인을 타지 않는다. 컬·드로우가 따로 도니 드로우
> 스레드가 프레임 N을 그릴 때 배열에는 이미 N+1의 행렬이 들어 있어 그림자가 밀리고 떨렸다.
> 지금은 셰이더가 `trans_world_to_clip_of_carcam` / `..._of_fieldcam`(그림자 카메라 NodePath를
> 셰이더 입력으로)을 받아 Panda가 드로우 시점에 같은 프레임의 장면 그래프에서 계산한다. 이름에
> 밑줄이 있으면 안 됨(`car_cam` → Panda가 밑줄로 단어를 나눠 "Too many words").

## 일시정지 · 메뉴 복귀

주행 중 **ESC = 일시정지** (물리·랩타임·엔진음 전부 정지). 일시정지 카드는 작은 메뉴로,
W/S(↑↓)로 고르고 ENTER로 실행, ESC는 바로 재개.

| 항목 | 퀄리파잉 | 그랑프리 |
|---|---|---|
| RESUME | ○ | ○ |
| **RESTART RACE** | — (매 랩이 이미 새 시도) | ○ 같은 레이스를 그리드부터, 인트로 없이 |
| EXIT TO MENU | ○ | ○ |

완주 후에는 ESC/ENTER 둘 다 메뉴로.

- **H = HUD 전체 숨기기/보이기** — 일시정지 카드까지 같이 사라지므로 멈춘 화면을 깨끗하게
  볼 수 있음. 설정은 HUD가 재생성돼도(전체화면 전환) 유지됨.
- **P (일시정지 중) = 일시정지 카드만 숨기기/보이기** — 순위표·랩타임 등 나머지 HUD는 그대로.
  카드가 숨겨진 동안 W/S/ENTER는 무시함(안 보이는 메뉴에서 ENTER로 레이스를 나가 버리지
  않도록). 다음에 일시정지하면 카드는 다시 보임.

### 화면 녹화 (F9)

F9로 녹화를 시작하고 다시 누르면 멈춤. 파일은 `Videos\FORMULA-AI\formula-ai_날짜_시각.mp4`.
게임 안에서 프레임을 읽어 인코딩하면 GPU 읽기 정지와 CPU 인코딩이 렌더러와 겹쳐 렉이 생기므로
(OBS도 "소프트웨어 부담 적은" 설정을 찾게 되는 이유), 게임은 아무것도 하지 않고
`recorder.py`가 `ffmpeg`를 옆에서 띄움: Windows 데스크톱 복제(`ddagrab`)로 게임 창만 잘라
GPU의 H.264 인코더(Intel Quick Sync → NVENC → AMF → 최후 수단 CPU x264)에 텍스처째로 넘김.
실측(vsync 켠 20대 GP, 1600x900): 녹화 중 프레임 시간 16.7 ms, 녹화 안 할 때 16.8 ms — 차이 없음.
영상은 평균 약 50 fps(GPU가 바쁘면 ffmpeg가 몇 프레임 떨굼), 약 25–30 Mbps.

- 화면에 보이는 그대로 찍으므로 창이 맨 앞에 있어야 함(전체화면이 이상적).
- 소리는 녹음되지 않음. 우상단 빨간 `● REC 00:12` 표시도 영상에 찍힘 → `REC_INDICATOR = False`.
- 설정은 `config.py`의 `REC_*`(키, fps, 비트레이트, 저장 폴더, ffmpeg 경로).
- 조각화 MP4라 게임이 죽어도 마지막 1초 전까지는 재생됨.

### 전체화면 (F11)

F11로 전환하며 메뉴·로딩 화면에서도 동작. Ursina의 `window.fullscreen`은 창이 어디 있든
**주 모니터**의 위치·크기로 창을 옮겨서, 세컨드 모니터에서는 전체화면이 되지 않았음.
`app.toggle_fullscreen()`이 창 중심이 있는 모니터를 OS에 매번 새로 물어 그 모니터를 테두리
없이 꽉 채우고, 다시 누르면 원래 위치·크기·테두리로 돌아감.

> 처음엔 ESC가 바로 메뉴로 나갔는데, "잘못 눌렀다"고 말할 방법이 없었음.
>
> 부수 효과 하나: 자세제어 표시가 `ESC`였는데 이제 일시정지 키와 이름이 겹침.
> 같은 시스템의 실차 다른 이름인 **`ESP`**로 바꿈 — 관람객에게 설명할 거리를
> 굳이 만들 이유가 없음.

`Game.destroy()`가 씬을 직접 반납함 — Ursina에는 씬 비우기 호출이 없어서 만든 것은 전부
손으로 돌려줘야 하고, 빠뜨린 것은 안 보이는 채로 계속 그려짐.

> 실제로 새고 있었음: 메뉴↔레이스 1회당 씬 자식이 **정확히 1개씩** 증가. 범인은
> `EngineSound`의 `Audio` — Ursina의 `Audio`는 Entity 서브클래스라 볼륨을 0으로 만들어도
> 노드가 남음. `destroy()`까지 해야 함. 수정 후 5회 반복에서 씬·UI 증가 **0**.
> 축전에서 하루 종일 도는 프로그램이라 이게 제일 중요한 검증이었음.

### 그랑프리를 여러 번 드나들면 렉이 걸리던 문제

위 검증은 **렌더 노드 수**만 셌는데, 진짜 누수는 그 밖에 있었음. 이 Ursina 버전의
`destroy()`는 **자식을 재귀적으로 지우지 않음** (소스에 재귀가 주석 처리돼 있음). 루트 노드는
사라져서 화면에는 안 보이지만 자식 Entity는 전부 `scene.entities`에 남고, Ursina는 그 목록을
**매 프레임 순회**함. HUD 하나가 자식 약 230개라 레이스 1회당 그만큼 쌓였고, 판을 거듭할수록
느려짐.

| 원인 | 1회당 누수 | 수정 |
|---|---|---|
| `destroy()` 비재귀 (HUD·메뉴·로딩 카드·차) | ~230 Entity | `ui.destroy_tree()`로 전부 교체 |
| Ursina `Circle` 메시 (만들 때마다 도우미 Entity 1개 남김) | 10 Entity | 정점을 1회만 구해 재사용 (`hud._disc`) |
| `Text` 폰트 세터: 매번 모델 경로 추가 + 글리프 캐시 `clear()` | 경로 ~160개 | `ui.install_font_cache()` |

수정 후 메뉴↔그랑프리 5회 반복: `scene.entities`, GC 객체, 렌더 스테이트 증가 **0**, 프레임
시간 일정.

## 노변 — Kenney 킷 에셋 배치

절차적 박스 대신 실제 모델을 씀. 서킷으로 **읽히는** 데 제일 크게 기여한 건 배리어 라인 —
실제 서킷은 경계가 있고, 코너에서 눈이 따라가는 게 그 경계임.

| 요소 | 에셋 | 실제 크기 | 배치 |
|---|---|---|---|
| 배리어 | barrierRed / White | — | 양쪽 가장자리 전체, 적응형 길이 |
| 그랜드스탠드 | grandStandCovered | 17.2 × 17.6 × **20.4 m** | 양쪽 벽의 직선 구간 전체 (서킷당 190~560모듈) |
| 패독 | tent | 9.9 × 9.9 × **6.9 m** | 반대편 2열 |
| 조명탑 | lightPostModern | **7.8 m** | 42 m 간격, 좌우 교대, 배리어 뒤 |
| 콘 | pylon | 0.44 m | 코너 인쪽 kerb 옆 |
| 체커기 | flagCheckers | 4.1 m | 스타트 라인 양옆 |

킷은 4.5 m GT카보다 작은 세계를 전제로 만들어져서 **소재 그대로 쓰면 그랜드스탠드가
차보다 작음**(3.3 × 3.9 m). 스케일 상수(`GRANDSTAND_SCALE` 등)로 트랙·차 비율에 맞춤.

관중석을 2배(20.4 m 높이)로 키우면서 **후퇴 거리를 높이에서 유도**하게 바꿈
(`max(3.0, h × 0.55) + 깊이/2`). 20 m 지붕선은 고도 22°에서 50 m 그림자를 만들고 그중
21 m가 트랙 쪽이라, 벽에서 3 m 뒤에 두면 그림자가 **중심선 1.4 m 지점**까지 덮음.
높이에 묶어두면 다음에 스케일을 바꿔도 상수가 낡지 않음.
타일 간격과 후퇴 거리는 상수가 아니라 **스케일된 에셋의 footprint에서 유도**해서, 스케일을
바꿔도 배치가 어긋나지 않음.

마커 포스트만 박스로 남김 — 킷에 대응 에셋이 없고, 차에 제일 가까워서 속도감의 핵심 단서라.

### 드로우콜을 지키면서 모델 쓰기 (`game/props.py`)

에셋 1개를 **템플릿으로 1회 로드** → 배치마다 `copy_to` → 마지막에 `flatten_strong()`.
노변 전체가 **배치 11개 = GeomNode 11개**.

> 삽질 3건. ① `flatten_strong()`이 **전혀 병합을 안 했음** (1500개 → GeomNode 1500개, 8.5초).
> panda3d-gltf가 메시마다 transform이 preserved로 표시된 ModelNode를 씌우는데 그걸 넘어서는
> 병합이 안 됨. **`clear_model_nodes()`** 를 먼저 부르면 됨 → 1 GeomNode, 0.97초.
>
> ② 배리어가 트랙을 **가로질러** 누워 있었음(빗살 모양). 모듈의 긴 축은 로컬 x인데 yaw 0은
> 모델을 +z로 향하게 함 → **+90° 필요**. 눈으로 판단하지 않고 배치된 바운딩박스를 재서 확인함.
>
> ③ 그랜드스탠드 타일링에 틈. 원인은 모듈 폭이 아니라 **중심선 샘플 간격이 5 m**라
> 3.3 m 타일이 같은 인덱스로 스냅된 것. 스타트 접선 방향 직선 보간으로 교체.
>
> ④ 가로등이 **트랙 방향(앞뒤)을 비추고 있었음**. 램프 팔은 모델의 z축으로 뻗는데
> "헤딩 + 90°" 규칙이 한쪽에서 부호가 뒤집혀 절반이 들판을 비춤. 방향 벡터에서 각도를
> 직접 계산하는 `yaw_towards()`로 교체.
>
> ⑤ 그런데 그것도 **정확히 180° 틀렸음**. 내가 쓴 검증(상위 20% 정점의 중심)은 이 에셋에서
> 기둥 꼭대기의 굽은 부분이 지배해서 램프 헤드가 아니라 **반대쪽**을 가리켰음 — 지표가
> 그럴듯해 보여도 재려던 것을 재고 있는지는 별개. 렌더 결과가 정답.

### 벽 = 중간축까지의 거리 (`Track.wall_offsets()`)

각 샘플을 자기 법선으로 고정 폭만큼 미는 방식은 **틀림**. 코너가 오프셋보다 급하면
오프셋 곡선이 코너 중심을 지나 **자기 자신을 통과해 접히고**, 두 구간이 가까우면 양쪽
벽이 서로를 뚫음. 몬자 1번 시케인은 둘 다 해당.

**물리 쪽 코리도어에는 이 문제가 없음** — `resolve_wall`이 **최근접 중심선 점**으로 재기
때문. 그건 거리장이고, 그 등위면은 급코너를 접히지 않고 **감싸는** 올바른 오프셋 곡선임.
그래서 벽도 그걸 쓰게 함.

닫힌 식으로 한 번에 구함. 광선 `p = c_i + u_i·t` 가 `c_i`와 `c_j`에서 등거리인 지점은

```
t = |c_j − c_i|² / (2 u_i · (c_j − c_i))
```

이고, 모든 j에 대한 최솟값이 **중간축(medial axis)까지의 거리**. 한 패스에 정확하고
두 실패 모드를 동시에 잡음 — 코너 안쪽 이웃은 `t = R`(곡률반경)을, 좁은 구간 반대편은
간격의 절반을 내놓음.

**기울기 제한**으로 매끄럽게: 침식+평균 스무딩은 낙차를 창 크기로 나눌 뿐이라
11 m 낙차를 9샘플로 퍼뜨려도 여전히 1.3 m 계단이고, 필요 없는 구간까지 벽을 당김.
대신 샘플당 변화량을 `seg_len × 6%`로 제한 — 값을 낮추기만 하고, 제약 근처에서만 작동하며,
벽이 얼마나 급히 꺾일 수 있는지에 **정확한 상한**을 줌.

**벽 메시 · 배리어 프롭 · 충돌 판정이 모두 이 한 줄을 공유**함. 보이는 벽과 부딪히는
벽이 어긋날 수가 없음.

23개 서킷 전수 측정:

| | 처음 | 중간축만 | +기울기 제한 |
|---|---|---|---|
| 최악 접힘 (Shanghai) | **+14.1 m** | +1.54 m | **+0.20 m** |
| Zandvoort | +12.0 m | 0.00 m | **0.00 m** |
| Montreal | +10.3 m | 0.00 m | **0.00 m** |
| 이웃 샘플 간 최대 단차 | — | 1.27 m | **0.31 m** |
| 접힘 0.00 m인 서킷 | — | 18 / 23 | **20 / 23** |

평균 오프셋은 19.0~19.8 m로 유지 — 필요한 곳에서만 좁힘.

### 관중석 배치 — 랩 전체

관중석은 **직선 건물**이다. 곡선 벽을 걸으며 모듈마다 가장 가까운 중심선을 바라보게 하면
같은 줄인데도 방향이 모듈마다 조금씩 달라지고, 스트레이트에서 그게 "살짝씩 어긋난 줄"로
보인다. 그래서 배치를 뒤집었다 — **벽 라인을 먼저 직선 구간으로 자르고**, 구간 하나당
방향 하나·원점 하나를 정한 뒤 그 직선 위에 모듈 폭 간격으로 타일링한다. 같은 줄의 방향
편차와 간격 오차가 계산 구조상 0이다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `STAND_STRAIGHT_TOL` | 6° | 이 이상 꺾이면 구간을 끊음 |
| `STAND_PERP_TOL` | 6 m | 벽이 구간 직선에서 벗어나도 되는 거리 |
| `STAND_COVERAGE` | 0.68 | 양쪽 벽 중 관중석이 차지할 비율(목표) |
| `STAND_MIN_GAP` | 8 m | 구간 사이 최소 간격 |

실측(몬자/스파/잔드보르트/상하이): **69 / 66 / 55 / 59 %** 커버, 겹침 **0**,
한 구간 내 방향 편차 **0.000°**. 몬자 기준 관중석 51 → 464모듈.

프레임 비용은 **0.15 ms** — 9배로 늘려도 사실상 공짜다. 전부 한 배치로 flatten되므로
드로우콜이 늘지 않는다(같은 측정에서 그림자 패스는 1.7 ms).

> 삽질 3건. 셋 다 "커버리지가 안 오른다"로 보였고, 셋 다 원인이 배치 로직 바깥에 있었다.
>
> **① 맞닿음을 겹침으로 셌다.** 한 구간의 이웃 모듈은 정확히 폭만큼 떨어뜨려 놓으므로
> 면이 여유 0으로 만난다. SAT가 이걸 겹침으로 판정해서 **모든 구간에서 한 칸 건너 하나씩
> 버리고 있었다.** 탈락 293건 중 282건이 "자기 구간의 바로 옆 모듈, 정확히 17.2 m 거리".
> 커버리지가 딱 절반에서 멈춰 있었고, 허용오차를 3°→14°로 쓸어도 48%에서 안 움직인 이유가
> 이것. 거부해야 하는 건 접촉이 아니라 **관통**이므로 0.10 m 여유를 둠.
>
> **② 구간 사이 진행을 샘플 개수로 계산했다.** `(길이 + 간격) / step`은 벽 점들이 step
> 간격이라고 가정하는데, 샘플은 **중심선** 기준이라 코너에서 바깥 벽은 더 벌어진다. 항상
> 짧게 진행해서 다음 구간이 이전 구간 **안에서** 시작했다.
>
> **③ 고쳐서 구간 직선에 투영했더니 더 나빠졌다.** 투영값은 트랙이 돌아서는 순간 증가를
> 멈추므로 목표치에 영원히 도달하지 못하고, **첫 번째 진짜 코너에서 그 사이드의 순회가
> 통째로 끝난다.** 스파가 4.2%로 붕괴. 곡률과 무관하게 단조 증가하는 **호길이**로 교체.

모듈 자체는 중심선이 아니라 **벽 라인을 호길이로 걸으며** 타일링한다 — 코너 20 m 바깥은
중심선보다 긴 호라서, 중심선 간격으로 놓으면 모든 코너 바깥에서 틈이 생긴다(배리어와 같은
함정).

> 이전 구현(구간별 최저속 코너 바깥에 한 덩어리씩)에서 겪은 삽질 3건, 전부 몬자 1번 시케인.
>
> **① 방향과 위치가 동시에 틀림 — 원인은 하나.** `_turns_left`가 30 m 창의 접선 차이로
> "코너 바깥"을 정하는데, 시케인은 관중석 길이(120 m) 안에서 곡률이 −0.054 → +0.051로
> 뒤집힘. 어느 로브에 걸리느냐로 결과가 정해지니 방향도 위치도 임의였음.
>
> **② 그래서 시케인을 건너뛰게 했더니** 몬자가 5.8 km에 관중석 3개만 남음. 실제 몬자는
> Rettifilo에 거대한 관중석이 있음.
>
> **③ 그래도 첫 모듈이 배리어를 0.98 m 뚫음.** 검사가 모듈 **중심**을 상수 여유로 보고
> 있었는데, ⓐ 회전한 박스의 **모서리**는 중심보다 1.75 m 더 뻗고(반대각 6.1 m vs 반깊이
> 4.4 m) ⓑ 벽 오프셋은 시케인에서 안쪽으로 당겨져 있어 같은 setback이 훨씬 가까운 위치가 됨.
> **모든 모듈의 네 모서리를 그 지점의 벽 오프셋과** 비교하도록 교체 — 이 검사는 현재
> 구현에도 그대로 남아 있다.

### 지면은 산까지 이어진다

잔디 평면을 트랙 바운딩 박스에 맞춰 자르면 산이 시작하는 곳보다 1 km쯤 앞에서 끝나고,
그 사이로 하늘이 비친다. `terrain.ring_bounds()`가 산 고리의 안쪽 반지름을 내보내고
평면은 거기에 맞춰 크기를 잡는다 — 반변이 그 반지름인 정사각형은 해당 원을 통째로
포함하므로(모서리는 산 밑으로 들어가 보이지 않는다) 어느 방향으로 봐도 지평선이 닫힌다.
산맥도 `Y_GRASS`에서 시작하게 내려 붙여 이음매의 턱을 없앴다.

### 회색 벽 제거

배리어가 같은 라인을 따르고 벽을 덮을 만큼 커진 뒤로 회색 벽 메시는 코너에서 직선 현
뒤로 비치기만 했으므로 삭제. **배리어가 곧 벽**이고, 충돌 판정은 같은 오프셋을 읽으므로
주행 가능 영역은 그대로.

### 배리어가 회색 벽에 듬성듬성 보이던 문제

두 가지가 겹쳐 있었음. ① 배리어를 클램프해서 당기면 고정 오프셋인 회색 벽에서 떨어져
나옴 → 위의 공유 라인으로 해결. ② 모듈이 **0.43 m인데 벽 메시는 1.1 m**라 걸레받이처럼
보였음 → 높이 2.9배(1.25 m), 깊이 1.5배(0.62 m)로 늘려 벽을 덮음. 코너에서는 직선 현이
곡선 벽 안쪽으로 들어가므로 0.20 m 바깥으로 밀어냄.

전광판(billboard)은 서킷 설비보다 광고판으로 읽혀서 제거.

### 적응형 배리어 길이

모듈은 0.83 m라 6 km 서킷 양쪽이면 1.4만 개. 대신 **길이 방향으로 늘려서** 배치하는데,
고정 피치는 제일 급한 코너 기준이라 직선에서 낭비가 큼. 그래서 가장자리가 곧게 유지되는
동안 하나의 모듈을 **탐욕적으로 연장**하고(최대 24 m), 3° 이상 꺾이면 끊음.

| Monza | 고정 5 m 피치 | 적응형 |
|---|---|---|
| 빌드 시간 | 2.18 s | **0.32 s** |
| 삼각형 | 130,958 | **80,108** |
| 레이스 시작 총 | 3.69 s | **2.20 s** |

코너 해상도는 그대로 — 직선에서만 길어짐.

## 주변 산 (`game/terrain.py`)

끝없는 평면 위의 서킷은 장소감이 없음 — 지평선이 직선이고 어느 방향이나 똑같음.
트랙 바운딩 원에서 400 m 밖부터 2.1 km 두께의 능선 하나를 극좌표 격자로 생성함
(128 × 14, 약 10k 삼각형, 드로우콜 1개). 지형만이고 나무·건물은 없음.

- 트랙 중심에서 충분히 멀리 시작하므로 서킷 모양과 무관하게 **트랙을 침범할 수 없음**.
  이 거리에서는 "중심까지의 거리"와 "트랙까지의 거리" 차이가 무의미하고, 정확한
  최근접 탐색은 정점마다 전체 탐색이 필요해 비쌈.
- 높이는 "얼마나 높아 **보여야** 하는가"에서 역산 — 능선이 약 2.3 km에 서므로 750 m면
  약 18° 를 차지함.
- 색은 차갑고 어둡게(청보라). 노을에 멀리 있는 산은 실루엣이고, 앞의 따뜻한 헤이즈가
  색을 다 만들어 줌. 초록으로 두면 그냥 잔디로 읽힘.
- 그림자 패스에서는 제외(`casts=False`) — 140 m 섀도우 필름 밖이라 받기만 하면 됨.

> 처음엔 안 보였음. `HAZE_END`가 3200 m라 2~4 km의 산이 하늘과 **같은 값**으로 뭉개졌음.
> 4800으로 밀고 `CLIP_FAR`를 1200 → 6000으로 올림(원거리 평면은 깊이 정밀도를 거의
> 좌우하지 않음 — 근평면이 지배한다는 건 이미 이 프로젝트에서 확인한 사실).

## 조명 — 골든아워 (`game/lighting.py`, `game/shaders.py`)

> 2026-10부터 기본은 `"day"` 프리셋이고 이 절의 골든아워는 `LIGHTING_PRESET = "sunset"`으로
> 남아 있음. 조명 모델도 선형 HDR + 물리 기반으로 바뀜 — 위 "그래픽" 절 참고. 아래 그림자
> 굽기·바이어스 기록은 그대로 유효함.

전용 셰이더 `sunset_shader`. Ursina의 `lit_with_shadows_shader`는 **앰비언트 항이 없고**
알베도에 광원색을 곱하는 걸로 대신하는데, 한낮 백색광이면 통하지만 노을에 쓰면
태양을 등진 면까지 주황이 됨 — 정확히 반대임.

실제로 저각의 빛이 따뜻한 건 **짧은 파장이 산란되어 빠져나갔기** 때문이고, 그 산란된
파랑이 나머지를 비춤. **따뜻한 키 + 차가운 필**. 이 관계 하나가 노을처럼 보이는지를 결정함.

```
색 = 알베도 × (하늘앰비언트 + 지면반사) + 알베도 × 태양색 × N·L × 그림자 + 스페큘러
     → 거리에 따라 지평선 헤이즈로 혼합
```

- **반구 앰비언트**: 법선이 위를 보면 하늘색(차가움), 아래를 보면 지면 반사(따뜻함).
  싸구려 GI 대용이고 비용은 mix 두 번.
- **랩 디퓨즈**: 저각 빛은 곡면을 길게 감싸므로 N·L 경계를 부드럽게 함.
- **스페큘러**: 저각 태양은 아스팔트와 차체에 긴 광택을 남김. 없으면 "어둡게 만든 한낮"이 됨.
- 하늘은 지평선→천정 2단 그라디언트를 절차적으로 생성. 방위각으로는 균일하게 둠 —
  돔 UV 매핑을 먼저 확정하지 않으면 태양 원반이 그림자 방향과 어긋나는데, 그건 눈에 즉시 보임.

### 셰이더 유니폼은 씬 루트에 — 단, `default_input`에 있으면 안 됨

Ursina는 셰이더를 엔티티에 할당할 때 `default_input`을 **엔티티마다** 설정하고,
엔티티 값은 상위 노드에서 상속된 값을 **덮음**. 그래서 매 프레임 값을 `scene`에 한 번만
쓰려면 그 키를 `default_input`에서 빼야 함. 지금은 진짜로 엔티티마다 다른 것
(`spec_strength`, `spec_power`, 텍스처 스케일)만 남겨둠.

카메라까지의 거리는 아예 유니폼을 없앰 — **뷰 공간에서 카메라는 원점**이므로
`length(view_position)`이면 충분함. 셰이더가 스스로 구할 수 있는 값을 밖에서 넣어주면
조용히 틀릴 여지만 생김:

> 몬자 1번 코너에서 차와 바닥이 주황으로 떡졌던 원인이 이것. `camera_world_position`이
> 원점에 머물러 헤이즈가 **월드 원점으로부터의 거리**를 재고 있었고, T1은 원점에서 940 m라
> 헤이즈 95%가 걸렸음. 셰이더 내부 값(cover/shadow/haze)을 R/G/B로 찍어보고서야
> 특정됨 — 그 전까지 세 번 잘못 짚었음.

### 노변이 통째로 조명을 안 받고 있었음 (`flatten_strong` + 셰이더 순서)

**`flatten_strong()`은 그 시점의 노드 상태를 지오메트리에 굽고, 거기에는 셰이더가 포함됨.**
그래서 flatten 뒤에 부모에 셰이더를 걸면 구워진 쪽이 이기고 **절대 실행되지 않음.**

`props.batch()`가 flatten을 하고 `Sunset.apply()`가 나중에 셰이더를 걸고 있었으므로,
**10개 노변 배치(배리어·관중석·천막·나무·콘·깃발·조명탑) 전부가 Ursina 기본 셰이더로
그려지고 있었음** — 태양도 그림자도 없이 정점 색만. "관중석 지붕이 계단에 그림자를
안 만든다"가 정확히 이것이었음.

최소 재현으로 확정함: 동일한 슬래브 3개에 각각 (a) flatten 안 함 (b) flatten 전에 셰이더
(c) flatten 후에 셰이더 → (a)(b)는 따뜻한 조명 + 위 블로커의 그림자, (c)는 회색·무광·무그림자.
`shadow`/`diffuse`/`cover`를 R/G/B로 찍었더니 (c)는 세 값이 전부 알베도와 같았음 —
셰이더가 아예 안 돌고 있다는 뜻.

수정: 셰이더를 `PropLibrary.batch()` 안에서 **flatten 전에** 걺.
머신 기준값 대비 비용은 7.32 → 7.37로 사실상 변화 없음(이미 그리던 지오메트리라).

### 수직면이 전부 같은 밝기로 보이던 문제

반구 앰비언트는 법선의 **위/아래 성분만** 보므로, 태양을 못 받는 수직면은 어느 방향을
보든 값이 같음 → 관중석 좌석이나 천막 옆면이 단색 판때기로 보임. 실제 노을 하늘은
태양 쪽이 훨씬 밝으므로 그 **방위 성분**을 추가함:

```
ambient += glow_color × max(0, dot(수평법선, 태양방향)) × 수평성분 × strength
```

> 참고로 **천막은 원래 면이 하나**임 — 기둥 위 평평한 캐노피라 위를 보는 면 말고는
> 음영이 갈릴 면이 없음. 잔디에 지는 그림자는 정상적으로 나옴.

### 시작선만 어둡던 문제

`Mesh(...)`에 `normals=`를 넣는 패치가 **시작선 지점만 매칭에 실패**해서 노멀 없이
생성되고 있었음. 노멀 열이 없으면 Panda가 셰이더에 아무 값이나 넘김 — 측정하니
`diffuse`가 아스팔트 0.54 대비 **0.33**(N·L 0.10 vs 태양 고도가 요구하는 0.38)이었음.
셰이더 중간값(shadow / albedo / diffuse)을 R/G/B로 찍어 특정함.

### 그림자 바이어스는 월드 단위가 아님

`shadow_bias`는 **정규화 깊이**라 실제 여유는 `bias × (far − near) = bias × 2 × SHADOW_DEPTH`.
0.0022 × 800 m = **1.76 m** — 리어윙이 엔진커버에 지는 그림자나 지붕이 좌석에 지는 그림자는
통째로 삼켜짐. 0.0004 × 600 m = 24 cm로 낮추니 자기그림자가 살아남(바닥 acne 없음).

### 그림자 비용과 베이크

같은 머신 상태에서 짝지어 측정 (1280×720, 기준 장면 2.21 ms):

| | 프레임 |
|---|---|
| 전체 | 16.17 ms |
| 그림자 끔 | **13.70 ms** (−2.47) |
| 맵 1024로 | 15.92 (−0.25) |
| PCF 2×2로 | 15.86 (−0.31) |
| 둘 다 | 15.59 (−0.58) |

즉 2.47 ms 중 **샘플링은 0.6 ms뿐이고 나머지 1.9 ms는 그림자 패스 자체** —
매 프레임 캐스터를 깊이 버퍼에 다시 그리는 비용. 해상도나 탭 수를 줄여봐야 소용없고,
**정적 지오메트리를 베이크해야 없어지는 값**임.

베이크의 이득은 그 1.9 ms + **140 m 커버리지 제한 제거**(지금은 차 주변 140 m만 그림자가
있고 경계에서 페이드됨). 비용은 셰이더에 그림자 맵이 둘 됨 — 서킷 전체를 덮는 정적 맵
하나와 차만 담는 작은 동적 맵 하나. 아직 구현하지 않음.

### 태양 각도는 서킷에서 유도

고정 방위각은 어떤 서킷에선 예쁘고 어떤 서킷에선 메인 관중석 뒤에 태양을 놓음.
**태양 쪽에 있는 높은 물체가 트랙에 그림자를 던지므로** 이게 결정적임:

| | 그림자 길이 | 트랙 횡방향 |
|---|---|---|
| 관중석 10.2 m, 고도 8.5° | 67 m | 트랙 전체 암전 |
| 고도 22°, 레이크 65° | 25 m | **11 m — 런오프에서 멈춤** |

그래서 방위각을 스타트/피니시 접선에서 유도(`SUN_RAKE`, `SUN_SIDE`), 고도 22°.

### 그림자 맵은 차를 따라감

6 km 서킷 전체를 한 장에 담으면 텍셀당 3 m — 차를 못 그림. 140 m 상자에 맞추면 7 cm.
바깥은 샘플이 무의미하므로 셰이더가 커버리지 경계에서 그림자를 1(밝음)로 페이드함.

> 삽질 3건.
>
> **① 아스팔트만 새까맸음.** 잔디는 멀쩡한데 트랙만 그림자 100%. 바이어스를 0.0022 →
> 0.05까지 올려도 그대로 → acne 아님. 추측을 멈추고 **그림자 값을 화면에 직접 그리니**
> 경계가 아스팔트 모양과 정확히 일치 = 자기그림자. 노면은 그림자를 **받기만** 하면 되므로
> 섀도우 카메라 마스크에서 제외(`apply(..., casts=False)`).
>
> **② 태양 각도를 바꿔도 화면이 안 변함.** Ursina의 `DirectionalLight`는 생성 시
> `render.setLight`을 부르는데 **아무도 해제하지 않음** — 셰이더가 읽는
> `p3d_LightSource[0]`가 세션 첫 레이스의 태양으로 고정됨. 메뉴↔레이스에서 두 번째
> 레이스부터 그림자가 깨졌을 버그. `destroy()`에서 `render.clear_light()`.
>
> **③ 부호를 반대로 잡아** `SUN_SIDE=-1`이 태양을 관중석이 아니라 패독 쪽에 놓았음.
> `d`는 빛이 **진행하는** 방향이라 태양은 그 반대편에 있음.

메시에 노멀이 없었으므로 추가함 — 노면 스트립은 평면이라 해석적으로 `(0,1,0)`,
마커 포스트는 **면별** 노멀(8정점 공유는 상자를 뭉갬). `Mesh.generate_normals`의 smooth
경로는 정점 리스트에 대해 O(n²)라 이 규모에선 끝나지 않음. 상자에 구워두던 상하 명암과
차 밑의 가짜 그림자는 제거 — 실제 조명이 하는 일을 두 번 하게 됨.

### 정적 그림자 굽기 — 원거리용 두 번째 맵

노변은 움직이지 않고 태양도 움직이지 않으므로, 그 그림자를 매 프레임 깊이 버퍼에 다시
그리는 것은 출력이 없는 작업이다. 레이스 시작 시 **서킷 전체를 덮는 맵에 한 번 그리고
버퍼를 꺼버린다**(`Sunset.bake()`).

다만 이걸로 따라다니는 맵을 **대체하지는 않는다.** 측정해 보니 그 교환이 나빴다.

| | 따라다니는 맵 | 구운 맵 |
|---|---|---|
| 텍셀 | 0.068 m (2048 / 140 m) | 0.46~0.74 m (4096 / 서킷 전체) |
| 도달 범위 | 차 주변 67 m | 랩 전체 |

굽기로 정적 그림자를 **전부** 대신하게 하면 프레임의 1.0~1.7 ms를 아끼지만, 가까운
관중석이 자기 아크네로 칙칙해지고 접지 그림자가 캐스터에서 떠오른다. 지붕이 계단에
드리우는 그림자는 0.7 m 텍셀로 표현할 수 없다. 그래서 **둘 다 유지하고 거리로 나눈다** —
가까이는 따라다니는 맵, `SHADOW_FADE_START`~`END` 밴드에서 넘겨주고 그 바깥은 구운 맵.
양쪽 다 같은 노변을 담고 있으므로 넘어갈 때 바뀌는 것은 **해상도뿐이고 내용이 아니다**.

결과적으로 **더 빠르다**. 교차 측정에서 구운 맵 조회를 켜는 쪽이 **0.59 ms 더 싸다**:
`cover`가 0인 곳에서 따라다니는 맵의 9탭을 통째로 건너뛰게 되는데, 직선에서는 화면
대부분이 그 영역이라 새로 추가된 4탭보다 절약이 크다. 그러면서 예전에는 아무 그림자도
없던 원거리에 그림자가 생긴다.

`BAKE_REPLACES_LIVE = True`로 하면 대체 모드(더 싸고 더 거침)를 쓸 수 있다.

> 삽질 5건. 굽기 자체보다 **좌표를 셰이더에 넘기는 데서** 다 나왔다.
>
> **① 라이트를 하나 더 만들었는데 버퍼가 안 생김.** Panda는 셰이더가
> `p3d_LightSource[i].shadowMap`을 참조할 때만 그 라이트의 섀도 버퍼를 만든다. 아무도
> 참조하지 않는 라이트는 아무것도 렌더하지 않는다. 게다가 두 번째 라이트는
> `p3d_LightSource` 배열에 끼어들어 **[0]이 태양이라는 기존 셰이더의 가정을** Panda의
> 정렬에 맡기게 된다. 전용 오프스크린 버퍼와 카메라를 직접 만드는 쪽으로 바꿈.
>
> **② 행렬을 어느 쪽으로 곱해야 하는지 안에서는 알 수 없었다.** `m * v`는 화면 전체를
> 그림자로, `v * m`은 전체를 밝음으로 만들었다. **둘 다 그럴듯해 보이는 좌표를 낸다** —
> 범위 안이고 부드럽게 변한다. Python 쪽 `xform_point`는 정확했으므로(중심 → 0.49,
> 0.48, 0.50) 행렬 대신 **그 함수로 측정한 기저 벡터 4개**를 넘기게 바꿔서 관례 문제를
> 아예 없앰.
>
> **③ 판별력 없는 검증을 하고 정답이라 믿을 뻔했다.** 중심선 점들의 텍셀을 읽어 봤는데
> 거기는 두 v 규약 모두 "빈 픽셀"이라 아무것도 구별하지 못했다. 결정적이었던 건 상수
> 좌표로 샘플러를 찌른 것(텍스처는 정상 → 좌표 문제)과 u,v를 화면에 칠한 것(전부 0).
>
> **④ 셰이더 브랜치는 유니폼 부재를 막아주지 않는다.** `bake_ready`가 0이라 접근하지도
> 않는 `bake_map`/`bake_matrix`를 Panda가 draw마다 요구함. 1×1 깊이 텍스처로 시드.
>
> **⑤ 필름을 "조였는데" 오히려 커졌다.** 카메라 중심 기준으로 `max|x|*2`를 잡았는데,
> 카메라는 트랙 바운딩 박스 중심에 있고 그 박스가 빔 좌표계에서 앉는 위치는 거기가
> 아니다. `set_film_offset`으로 실제 내용에 맞춤.
>
> **⑥ 깊이가 어느 축인지 문서와 달랐다.** Panda의 카메라는 +y를 보고 +z가 위이므로
> 필름은 x/z, 깊이는 y — 그렇게 짰다. 실제로 나오는 값은 그렇지 않았다. **서로 다른
> near/far 두 설정으로 정규화해도 같은 원본 값(−1045)이 나왔고**, 그 값은 카메라 y가 아니라
> **z** 범위 안에 있었다. 결과는 두 가지였다. 서킷 일부가 깊이 범위 **밖**으로 나가는데,
> 기준 깊이가 0보다 작으면 비교를 전부 통과하므로 **그 지점들은 구운 그림자를 아예 잃는다**
> — 몬자 마지막 코너에서 "가까이 가면 그림자가 생기는" 증상이 이것이었다(근거리 맵에는
> 있고 구운 맵에는 없으니 넘어가는 순간 튀어나온다). 그리고 필름을 깊이 범위로 잡는 바람에
> 텍셀의 3분의 2를 버리고 있었다(0.74 → **0.55 m**, 잔드보르트는 0.35 m).
>
> 이번에도 결정적이었던 건 값을 찍어 본 것이다. R=구운 맵, G=근거리 맵, B=cover로 칠하니
> 관중석은 초록(구운 맵이 그림자 처리)인데 지면만 마젠타(구운 맵은 밝다고 함)로 갈렸다.
> 그 전에 세운 가설 두 개 — 노멀 오프셋, 뒷면 기록 — 은 둘 다 렌더로 반증됐다.

이제 렌즈 설정 후 **서킷 전체가 깊이 [0,1] 안에 들어오는지 검사**하고, 벗어나면 경고를
찍는다. 관례를 다시 추측하는 대신 검사하는 쪽이 싸다.

아크네 대응은 두 가지. **깊이 바이어스가 아니라 노멀 오프셋** — 0.74 m 텍셀에서 저장된
깊이는 최대 한 텍셀 옆의 깊이이므로, 이를 덮을 만큼 깊이 바이어스를 키우면 모든 그림자가
캐스터에서 떠오른다. 조회 지점을 표면 노멀 방향으로 2텍셀 밀면 오차가 실제로 있는
방향으로 움직이므로 바이어스는 0.35 m로 충분하다. 그리고 굽기 카메라는 **뒷면을**
기록한다 — 캐스터의 앞면이 곧 자기 자신과 깊이 비교를 하게 되는 면이라, 물체 두께만큼
띄워두면 그 비교가 실패할 일이 없다. 여기 프롭은 닫힌 솔리드라 새지 않는다.

경계선은 `SHADOW_FADE_START`를 0.38 → 0.23으로 낮춰 넘겨주는 구간을 14 m에서 35 m로
넓혀 감췄다. 텍셀 크기가 11배 바뀌는 전환을 좁은 밴드에서 하면 땅에 선으로 보인다.

> **덤으로 찾은 누수:** Panda는 그림자를 던지는 라이트의 깊이 버퍼를 GSG 안에 만들고,
> 그 라이트를 소유한 Ursina 엔티티를 destroy해도 **회수하지 않는다.** 레이스 1회당
> 2048 버퍼 하나. 씬 그래프 자식 수는 평평하므로 그걸 세는 검사로는 안 보이고, 엔진의
> 버퍼 개수를 세야 보인다. 축전처럼 메뉴↔레이스를 종일 반복하면 메모리가 마른다.
> `destroy()`에서 명시적으로 `remove_window`.

### 벽 충돌 — 차체 상자와 접촉점

예전에는 **차체 중심 한 점**만 벽 오프셋과 비교했다. 차 절반이 배리어에 박힌 뒤에야
감지되고, 무게중심을 지나는 힘은 모멘트가 0이므로 **어떤 충돌도 차를 돌리지 못했다.**
둘 다 같은 누락이다 — 차체에는 크기가 있다.

이제 4.45 × 2.41 m 상자의 **네 모서리**를 검사하고, 비교 대상은 중심선 오프셋이 아니라
**배리어 폴리라인 그 자체**다. 가장 깊이 박힌 만큼 밀어내고, **배리어 안에 들어간
모서리들의 중심**에 임펄스를 준다 — 정면 충돌이면 두 모서리라 팔이 차체 중심선에 놓여
안 돌고, 스치면 한 모서리라 돈다.

**보이는 배리어와 부딪히는 벽이 같은 물건이어야 한다.** 예전에는 프롭이 벽선의 현을 따라
놓이고, 충돌은 *가장 가까운 중심선 샘플*의 벽 오프셋과 비교했다. 직선에서는 두 곡선이
일치하지만 코너에서는 다르다 — 현은 자기가 잘려 나온 호를 벗어난다. 4개 서킷 실측 결과
**보이는 배리어가 차가 실제로 멈추는 벽보다 최대 4.97 m 바깥**에 있었다. 러너오프 한복판
에서 아무것도 없는 곳에 튕기고, 배리어는 몇 미터 떨어져 있었다.

`Track.barrier_lines()`가 그 현들을 만들고, 프롭 배치와 충돌 판정이 **같은 배열**을 읽는다.
`Surface`는 각 세그먼트의 랩 위치를 색인해 두고 차 주변 것만 검사한다.

| 서킷 | 수정 전 (계통 오차) | 수정 후 (평균 \|오차\|) |
|---|---|---|
| Monza | 최대 +1.97 m | 0.03 m |
| Spa | 최대 +2.95 m | 0.02 m |
| Shanghai | 최대 +4.97 m | 0.03 m |
| Zandvoort | 최대 +1.58 m | 0.02 m |

관통은 반슬래브가 아니라 **반공간**으로 판정한다: 88 m/s의 한 스텝은 1.5 m를 가는데 레일
두께는 0.6 m라, 슬래브로 재면 프레임 사이에 배리어를 그대로 통과해 버린다.

> 검증에서 두 번 헛짚었다. 처음엔 차체 **중심**의 거리를 쟀는데 반폭 1.205 m가 그대로
> "오차"로 잡혔고, 다음엔 이분법으로 첫 접촉을 찾으려 했다 — 히트가 반지름에 대해 단조가
> 아니다. 배리어 바깥으로 나가면 최근접 샘플이 랩의 다른 구간으로 넘어가 판정이 다시
> "안 닿음"이 된다. 전진 탐색으로 바꿔야 실제 첫 접촉이 나온다.

```
j = -(1+e) · v_contact·n / (1/m + (r×n)²/I)
```

접선 방향은 법선 임펄스로 상한을 둔 쿨롱 마찰. 이전의 `WALL_SPEED_KEEP`은 접촉마다 속도
전체에 0.55를 곱했는데, 스치나 정면으로 박으나 같은 대가를 물리는 건 거꾸로다.

`tools/smoke_headless.py` 실측(45 m/s로 진입):

| | 관통 | 최대 스핀 | 최저 속도 |
|---|---|---|---|
| 2° 스침 | 0.00 m | 28.5°/s | 137.6 km/h |
| 20° 클립 | 0.00 m | 215.1°/s | 92.9 km/h |
| 85° 정면 | 0.00 m | 97.4°/s | 8.7 km/h |

> 처음 쓴 테스트는 **스침 케이스가 벽에 닿지도 않았다.** 12 m 떨어져서 2°로 2초를 달려도
> 3 m밖에 못 좁힌다. "스침이 정면보다 속도를 덜 잃는다"는 단언이 통과했지만 아무것도
> 검증하지 않고 있었다. 시작 거리를 2 m로 줄이고, 접촉이 실제로 일어났는지를 단언에
> 추가함.

## AI 상대 — 고스트 (`game/ghost.py`)

리플레이가 아니다. 고스트는 플레이어와 **같은 차량 모델**을 자기 `Surface` 위에서 돌리고,
`autopilot.py`의 물리 플래너가 운전한다 — 녹화된 라인을 되풀이하는 게 아니라 서킷에
반응하고, 그 트랙에서 랩을 먼저 녹화해 둘 필요가 없다. 플레이어와 서로 충돌하지 않는다.

**학습은 하지 않았고, 필요하지도 않았다.** 플래너는 이미 마찰원과 요 밸런스에서 코너 속도를
유도한다. 난이도 손잡이 `pace`는 "타이어 그립의 몇 퍼센트까지 쓸 것인가"라는 물리량이라,
같은 드라이버가 덜 몰아붙이는 것과 같다. 실측 랩타임:

| pace | 0.80 | 0.88 (기본) | 0.94 | 1.00 | 1.06 | 실제 GT3 |
|---|---|---|---|---|---|---|
| Monza | 129.7 | 126.8 | 124.9 | 123.1 | 121.6 | ~107 |
| Zandvoort | 121.5 | 117.3 | 114.6 | 112.2 | 110.1 | ~96 |
| Spa | 165.7 | 160.3 | 156.6 | 153.2 | 150.1 | ~137 |

즉 8초 폭으로 연속 조절되고, 서킷마다 다시 학습시킬 필요가 없다. 학습된 정책은 이 둘을
모두 잃는다 — 서킷마다 재학습해야 하고, 다이얼을 돌릴 수 없다. **절대적으로 더 빠른 AI가
필요하다면** 그때는 학습이 답이지만(레포에 NEAT가 이미 있다), 관람객이 상대할 목표로는
121~130초가 이미 충분히 빠르다.

### 갭 표시

미터가 아니라 **같은 지점에서의 시간차**다. 한 코너 앞선 차가 한 코너만큼 빠른 것은 아니고,
드라이버가 손댈 수 있는 단위는 초다. 고스트는 중심선 샘플마다 "이번 랩 몇 초에 여기를
지났는가"를 기록하고, 플레이어의 현재 인덱스에서 그 값을 뺀다. 플레이어가 앞서 있으면
고스트가 아직 거기 도달하지 않았으므로 **직전 랩**의 기록을 쓴다.

> **랩 경계에서 갭이 −132초로 튀었다.** 결승선 인덱스는 랩의 끝이자 시작이다. 기록을
> 크로싱을 관통해 채우면 그 인덱스에 **이전 랩의 끝 시간**이 들어가고, 다음 랩에서 막 선을
> 넘은 플레이어(랩타임 ≈ 0)를 한 바퀴짜리 시간과 비교하게 된다. 선 앞뒤를 각각의 랩에
> 나눠 채우도록 고쳤다. 수정 후 갭 범위 −0.008 ~ +1.533초.

### 아웃랩

**퀄리파잉만** 첫 바퀴가 아웃랩이다. 계측하지 않고 HUD 랩 상자는 `OUT` — 스탠딩 스타트가
섞인 시간은 랩타임이 아니다. **그랑프리에는 아웃랩이 없다**: 레이스는 소등 순간부터 계측되고
1랩부터 센다(그리드는 결승선 6 m 뒤라, 출발 직후의 첫 크로싱은 armed 규칙 때문에 랩으로
세지 않는다).

`tools/ghost_check.py`가 그랑프리 한 판을 헤드리스로 돌려 랩 번호가 1에서 시작하는지, 갭이
매 랩 0 근처로 돌아오는지, 느린 쪽이 느린 랩을 내는지 확인한다. 물리 스모크로는 못 잡는다 —
고스트는 Ursina 엔티티를 들고 있어 창이 필요하고, 랩 규칙은 레이스 상태 기계에 있다.

## 세션 모드 — 퀄리파잉 / 그랑프리

### 퀄리파잉 (`game/replay.py`)

상대는 살아 있는 AI가 아니라 **AI의 가장 빠른 PERFECT 랩 한 바퀴를 녹화한 것**이다
(PERFECT = 네 바퀴가 모두 흰 선 밖으로 나간 물리 스텝 0, 벽 접촉 0 — 학습 도구의 tier-0과
같은 기준). 매번 같은 차가 같은 라인으로 달리니 어디서 지는지 배울 수 있다.

```bash
../.venv312/Scripts/python.exe tools/record_ghost.py --circuit Monza   # 또는 --all
```

AI가 플라잉 랩 5개를 헤드리스로 달리고, 깨끗한 랩 중 최고 기록만 `assets/ghosts/<서킷>.npz`에
물리 스텝마다의 차량 상태로 저장한다(재생은 시간 보간이라 PHYSICS_HZ가 바뀌어도 된다).
녹화 파일이 없는 서킷은 고스트 없이 혼자 달린다.

- 아웃랩 동안 고스트는 없다. 플레이어가 결승선을 넘어 **플라잉 랩을 시작할 때마다** 고스트도
  선에서 같이 출발한다.
- 고스트가 먼저 선에 도착하면 그 자리에서 사라지고, 플레이어의 다음 랩 시작과 함께 다시 나온다.
- **트랙 이탈(네 바퀴 모두 흰 선 밖) 한 스텝이면 그 랩은 삭제**된다. 시간은 빨간색으로 계속
  보여주고 `LAP INVALID` 플래그가 뜨지만 베스트 랩·섹터 베스트에 들어가지 않는다. R(리셋)도 삭제.
- 랩타임 상자 헤더에 고스트 대비 실시간 델타(앞서면 초록). 녹화가 한 바퀴 전체라 고스트가
  사라진 뒤에도 읽힌다. 타워는 베스트 랩 순, 1위는 `POLE`.

### 그랑프리 — 20대 필드 (`game/field.py`, `game/fieldproc.py`, `game/gpfield.py`)

플레이어 1대 + AI 19대(10팀 × 2, `game/teams.py`, 이름은 가상)가 그리드에서 소등 출발한다.
접촉·슬립스트림·DRS(2랩째부터, 앞차 1초 이내 직선)가 모두 실제로 작동한다. 플레이어 자리는
로소 코르사의 두 번째 시트다. 그리드는 예선 순서이고, 같은 서킷·같은 난이도에서 퀄리파잉
기록이 있으면 그 기록으로, 없으면 `GP_PLAYER_GRID`(기본 10번)에 선다.

- **AI는 별도 프로세스에서 돈다.** 19대의 판단과 물리는 파이썬으로 틱당 수 ms라 렌더 스레드에
  둘 수 없다. 게임은 매 프레임 "세션 시각 T까지 진행, 플레이어 차는 지금 이 상태"를 보내고,
  워커가 보낸 최신 스냅샷을 각 차의 속도로 그 프레임 시각까지 외삽해 그린다(지연 약 1프레임).
  플레이어 물리는 게임 쪽 120 Hz 그대로라 조작 지연이 없다. 접촉이 플레이어 차에 준 변화는
  스냅샷에 실려 와 게임이 적용한다.
- **계획 해가 없는 서킷**은 예전처럼 AI 고스트 1대와 달린다. 해는 `tools/solve_all.py`가 만든다.
- **접촉이 순간이동처럼 보이지 않게**: 접촉의 속도 변화는 바로, 밀어내는 위치 보정은 플레이어
  차에서 물리 스텝 몇 개에 걸쳐(시정수 40 ms) 넣는다. AI 차는 새 스냅숏이 이전 스냅숏의 외삽과
  다른 만큼을 그리는 위치의 오프셋으로 두고 70 ms 시정수로 줄인다(3 m 넘게 다르면 리셋 등이라 컷).
- **구조물 다리 충돌**: 출발 갠트리 다리와 관람 다리(섹터 구분) 기둥은 모델 치수 그대로의 상자로
  충돌한다(`game/structures.py` — 배치 계산을 경치와 물리가 공유, AI 워커도 같은 코드). 다리가 차
  폭보다 좁아 모서리 검사로는 코가 통과하므로 상자 대 상자 분리축 검사.
- **충돌 소리** (`game/impactsound.py`): 녹음 없이 합성 — 카본이 깨지는 고음 크랙, 차 질량의 낮은
  쿵, 비조화 패널 공명, 큰 충돌엔 파편 알갱이와 늦게 떨어지는 조각. 가벼움/중간/큼 × 변형 3개를
  `assets/audio`에 한 번 써 두고 피치를 흔들어 재생. 벽에 대고 갈면 스크레이프 루프. 내 차는 속도
  변화량으로, 다른 차끼리의 충돌은 카메라와의 거리로 음량을 정한다.
- **다른 차 바닥 불꽃**: 카메라 70 m 안의 AI 차도 175 km/h 이상에서 스키드블록 불꽃을 튄다(차마다
  다른 리듬).
- **옐로 플래그**: AI는 구간에서 75%, 멈춘 차 앞 100 m부터 옆까지 50% 페이스(Monza에서 평소
  201 km/h인 지점을 102 km/h로 지나감). 해당 구간은 미니맵에 노랗게 칠해지고, 레이스
  컨트롤이 "SLOW DOWN · NO OVERTAKES"를 안내한다. 옐로는 최소 15 s, 차가 다시 움직인 뒤에도 8 s
  더 유지된다. 내가 옐로 구간 안에 있으면 화면 테두리가 노랗게 깜빡이고 상단 박스가 SLOW DOWN을 안내한다.
  복구 중인 차는 지나가는 차 사이 틈을 기다리되 3 s 뒤부터 조건을 풀고 22 s 뒤엔 그냥 합류한다(전엔
  25 s 넘게 잔디 옆을 기어갔다). "감속 안 함" 판정의 기준 랩은 옐로 중 기록을 제외한 가장 최근의 깨끗한 랩이고
  플랜 속도의 80% 아래로는 내려가지 않는다. 미니맵의 옐로 구간은 어두운 띠 위의 굵은 노란 띠라 차 점에 가려지지 않는다. 우승자가 들어온 뒤
  마지막 차들은 우승자 마지막 랩의 1.4배(최소 60 s) 안에 못 들어오면 그 시점의 랩 수로 순위를 매긴다
  (결과 카드가 RUNNING에 멈춰 있던 문제). 첫 코너에서 줄 서 있던 차들은 이제 시속 12 m(약 43 km/h) 아래에서는 옆 차에게 길을
  양보하지 않는다(옆 차와 나란히 기어가다 멈춰 서서 줄줄이 옐로가 되던 문제; Monza 60 s 동안 시속 5 m 아래로
  기는 차-초가 22/20/34 → 9/5/16). 출발 후 6 s 동안은 복구 중이어도 옐로를 내지 않고, 옐로가 끝난 뒤 남는 구간은
  차를 따라 움직이지 않고 그 자리에 고정된다. 관전 중인 차는 서버 위치 보정을 더 길게(0.3 s) 풀어 카메라가
  덜 튄다. 메시지가 쌓이면 개수에 비례해 한 건당 표시 시간을 줄인다(최소 1.6 s).
- **출발 순위 선택**: 그랑프리 서킷 선택 화면에서 **A / D**로 내 출발 순위를 고른다 — `LAST QUALIFYING`(이 서킷·
  난이도에서 퀄리파잉으로 낸 기록, 없으면 P10) 다음 P1(폴)~P20. 세션 동안 유지된다(`SESSION["grid"]`,
  `grandprix.seats(player_grid=)`).
- **레이스 역동성** (`config.GP_*`): 퀄리파잉 순서가 곧 결승 순서가 되어 출발 뒤 추월이 거의 없던 것을 풀었다
  (스타트 60 s 이후 추월 0~3회). 드라이버마다 그날의 컨디션(`GP_FORM_SPREAD` 2%, 퀄리파잉엔 영향 없음)과 랩마다
  새로 뽑는 페이스 편차(`GP_LAP_VARIATION`)를 주고, 브레이킹 실수 확률(`GP_EXTRA_MISTAKES`)을 올렸으며 실수
  셋 중 하나는 제동을 0.9 s 놓치는 락업이다. DRS는 1.8 s 안에서 항력 35%로 세게(`field.DRS_*`), 공격은 코너
  낙차 18 m/s부터(`ATTACK_DROP`), 공격 중에도 페이스를 낮추지 않는다(`ATTACK_PACE` 1.0). 3랩 시뮬레이션:
  Monza 스타트 60 s 이후 추월 3 → 15, 접촉 2 → 13, 옐로 1 → 4; Austin 7 / 9옐로.
- **복구(OUT) 합류 보장**: 복구 중 "브레이크만 밟고 제자리에 서 있거나 빙빙 도는" 현상의 뿌리는 차가 **후진을
  못 한다**는 것이었다 — 정지 상태에서 브레이크로 후진하려 해도 저속 컷오프(`LOW_SPEED_CUTOFF`)가 매 스텝
  속도를 0으로 만들었다. `Controls.reverse`가 켜져 있으면 컷오프를 건너뛰어 후진한다(그리드·정지 때의 일반
  브레이크는 그대로 정지). 그 위에 규칙 셋: (1) 길에서 먼 곳이나 엉뚱한 방향이면 대기 지점을 향해 사람처럼
  운전한다(`_goto`: 향해 가다가 뒤쪽이면 후진, 벽에 박히면 물러나 다시 시도), (2) 단계마다 시간제한
  (`RECOVER_PHASE_T`)을 넘으면 후진+반대 핸들로 재시도하고, (3) 재시도 3번 또는 30 s가 지나면 마셜이 도로 가장자리에
  차를 올려놓는다(`Field._marshal`, 4 s 동안 다른 차와 겹쳐도 통과). 도로 밖 1.5~37 m, 임의의 방향으로 놓은
  차 52대가 모두 복귀(평균 5~14 s). 같은 상황에서 마셜 투입은 52대 중 약 60% → 3대.
- **"앞이 비었는데 멈췄다 가기"**: 앞차가 지나간 지점의 속도를 그대로 따라 하던 규칙 때문에, 한 곳에서 서행한
  흔적이 뒤 차마다 같은 자리 서행으로 복사되고 있었다(Monza T1에서 두 줄이 신호등처럼 멈췄다 감).
  코너 때문에 느린 것만 따르도록 자기 플랜 속도의 70%를 하한으로 둔다(`TRACE_FLOOR`).
- **관전**: 서킷 선택 화면에서 **G** — 퀄리파잉은 그 레벨 폴 랩 고스트를 계속, 그랑프리는 AI 19대
  레이스(내 자리는 비움). G로 순위 아래로, SHIFT+G로 위로 차를 바꿔 보고, ESC로 언제든 나간다.
- **그리드 박스**: 그랑프리 필드가 실제로 차를 세운 자리마다 노면에 흰 브래킷(코 앞 가로선 +
  뒤로 짧은 다리)을 칠한다(`trackmesh.grid_boxes`).
- 렌더링: 카메라 40 m 밖의 차는 재질별로 합친 평탄화 사본(15 → 5 드로우콜)으로 그리고,
  가까운 차만 바퀴 조향·회전, 차체 롤·피치를 매 프레임 계산한다.

**레이스 컨트롤** (`game/racecontrol.py`) — 원칙은 "내 잘못이 아니거나, 이미 시간으로 대가를
치른 실수에는 벌을 주지 않는다".

| 상황 | 처분 |
|---|---|
| 접촉 직후 1.5초 안에 트랙 이탈 | 없음 (밀려난 것) |
| 이탈했지만 스핀·크게 감속·5초 넘게 밖 | 없음 (이미 시간 손해) |
| 복구(OUT)를 거친 뒤 6초 안에 끝난 이탈 | 없음 (이미 시간 손해, 잔디를 가로질러 돌아오는 건 커팅이 아님) |
| 넓게 나갔다가 속도 유지 | 트랙 리밋 경고 1 → 2 → 3번째에 흑백기, 4번째부터 레벨별(Novice 0초, Rookie·Amateur 1초, Club 이상 2초) |
| 이득을 본 이탈(커팅, 0.2초 이상) | `ceil(2 × 번 시간) + 1`초, **최소 5초**(트랙 리밋 중 가장 무거움), 10초를 넘는 큰 커팅은 번 시간 + 10초 |
| 뒤차가 3 m/s 넘게 접근하며 추돌 | 뒤차 과실 |
| 나란히 달리다 옆으로 밀고 들어감 | 밀고 들어간 쪽 과실 |
| 과실 + 피해 차가 스핀·이탈·복구 또는 강한 충격 | 5초 |
| 과실이지만 가벼운 접촉 | 경고(반복 시 레벨에 따라 5초), 첫 랩에는 조치 없음 |
| 과실을 가릴 수 없는 접촉 | "레이싱 인시던트 · 조치 없음"을 플레이어에게 표시 |
| 옐로 구간에서 추월 (사고 차 제외) | "자리 돌려주기" 지시. 10초 안에 돌려주면 조치 없음, 아니면 5초. 옐로가 나온 지 2초 안의 추월은 제외(이미 나란히 달리던 추월, 반응 시간) |
| 옐로 구간에서 감속 안 함 | 자기 직전 랩의 같은 지점 속도와 비교해 평균 96% 넘게 달리면 첫 번째는 경고, 반복은 5초(레벨 4 이상). 1랩째는 비교할 랩이 없어 판정 안 함 |

이득 판정은 "그 구간을 트랙 위에서 달렸다면 달려야 했던 거리 − 실제 달린 거리"다. 트랙 안쪽
라인을 타는 것은 이득이 아니도록 중심선 진행 거리를 횡위치로 보정하되(1 − κ·n), n은 트랙 폭
안으로 제한한다. 제한하지 않으면 인필드를 가로지르는 커팅도 "아주 안쪽 라인"으로 보여 공짜가
된다. 페널티는 F1처럼 결승 후 레이스 타임에 더해진다. 2초 넘게 거의 멈춘 차나 복구 중인 차
앞 250 m는 옐로 플래그 구간이고(출발 직후 6초는 제외 — 그리드 전체가 아직 느리므로), 그
구간에서는 **모든 차의 제한 속도가 100 km/h**(`config.YELLOW_SPEED_KMH`)다. 구간에 들어선 뒤
3초 안에 제한 속도 아래로 내려와야 하고(300 km/h에서 차 한 대 길이로 설 수는 없다), 그 뒤
105 km/h를 1초 넘게 넘기면 "FAILING TO SLOW FOR YELLOW FLAGS" — 처음은 경고, 반복하면 5초.
HUD에는 `YELLOW FLAG · KEEP BELOW 100 KM/H · NO OVERTAKES`가 뜬다. AI는 구간 시작 320 m 전부터
18 m/s² 감속 곡선으로 미리 줄여 구간 안에서 제한 속도의 94%로 달리고, 앞 60 m 안의 달리는 차는
어느 차선에 있든 따라가기만 한다 — 사고를 피해 옆으로 비킨 차를 제치는 것도 추월이다. AI와
스튜어드가 같은 구간 정의를 쓰므로 AI가 벌받을 자리에서 레이스하지 않는다(한 대를 코스에 세워 둔
시뮬레이션에서 구간 안 최고 속도 94~96 km/h, 옐로 위반 0).

옐로가 나오면 모두에게 "YELLOW FLAG · SECTOR n · 차 STOPPED/RECOVERING", 끝나면 "TRACK CLEAR ·
GREEN FLAG"를 띄우고, 타워에서는 그 차의 칩(OUT/STOP)이 노란색, 트랙 맵에는 옐로 구간이 노랗게
칠해진다.

레이스 컨트롤 메시지는 **대기열**로 하나씩 보여 준다. 박스는 화면 위에서 내려오고 끝나면
올라가며, 다음 메시지로 바뀔 때는 올라갔다가 새 메시지로 내려온다. 내 메시지가 먼저, 다른 차 소식은 그다음
(12초 넘게 기다린 다른 차 소식은 버림). 줄이 서 있으면 메시지당 최소 2.5초, 헤더에 "N MORE".
OFF TRACK이나 옐로 표시에 가려진 동안은 메시지 시간이 흐르지 않는다. 박스 폭은 글자에 맞춘다.

`tools/session_check.py --only limits` (Monza): 넓게 나감 = 경고만 0초, 접촉 직후 = 면제,
시케인 커팅(1.74초 이득) = 4초, 큰 커팅(63초 이득) = 73초.

### 난이도 (`game/teams.py`)

① 드라이버가 달리는 계획(낮은 그립으로 푼 해일수록 일찍 브레이크를 밟고 코너를 천천히 돈다.
그래도 그 그립에서는 최적 라인이다), ② 엔진 출력, ③ 랩마다의 편차와 실수 빈도,

### 순위 타워 (`game/hud.py`)

20줄 타워: 순위 · 팀 색 · 세 글자 이름 · 앞차와의 간격(TAB을 누르면 선두와의 차이), 출발 대비
순위 변동(▲▼), 최고 랩 보라 점, 플레이어 줄 하이라이트, 타워 밖 칩(+5S 페널티, DRS, 복구 중
OUT). 순서가 바뀌면 줄이 새 자리로 미끄러진다. 헤더 아래 띠는 레이스 중 초록, 옐로 플래그면
노랑, 체커기 이후 체크무늬다. 간격은 F1 타이밍처럼 같은 지점(5 m 간격의 타이밍 루프)을 지난
시각 차이이고, 초당 10번 갱신한다. 칩은 타워 오른쪽 끝에 글자 폭대로 붙고, 2개면 옆으로 밀린다.
G로 관전 중인 차의 행은 빨갛게 표시된다. 레이스 컨트롤 박스와 ONBOARD 카드는 글자 길이에 맞춰 폭이 바뀐다.

숫자 표시(속도, 랩 시계, 간격)는 `hudkit.DigitField`다. 글자 칸 위치를 HUD를 만들 때 고정해 두고,
값이 바뀌면 각 칸이 폰트 페이지에서 어느 숫자 이미지를 쓸지만 배열 한 번에 바꾼다. 정적
패널·글자와 매 프레임 바뀌는 것을 다른 메시로 나눠, 갱신 때 작은 버퍼만 다시 올린다.
`tools/bench_hud.py`로 측정한다(20줄 간격이 매 프레임 전부 바뀌는 최악 조건 1.36 ms,
게임에서는 10 Hz 갱신이라 그보다 적다).

### 전 서킷 계획 계산 (`tools/solve_all.py`)

서킷마다 그립 0.97 → 0.94 → … → 0.74의 해를 차례로 푼다(첫 해만 콜드, 나머지는 바로 위 해에서
웜스타트). 끝나면 게임 물리로 한 바퀴 검증하고, 레벨별 예선 고스트 랩을 녹화한다. 이미 있는
해는 건너뛰니 중간에 끊었다가 다시 돌려도 된다.

```bash
../.venv312/Scripts/python.exe tools/solve_all.py            # 한 번에 한 서킷 (기본)
```

> **병렬로 돌리면 전부 실패한다.** 처음에 3개를 동시에 돌렸더니 해석기 하나가 메모리를
> 1~2 GB씩 써서, 브라우저 등과 합쳐 이 노트북(15.6 GB)이 바닥났다. 모든 해가 몇 초 만에
> `Insufficient_Memory`, `bad_alloc`으로 죽었다. 지금은 기본이 한 번에 하나다. 해를 시작하기 전에
> 여유 메모리를 기다리고, 메모리 때문에 죽은 해는 실패로 치지 않고 다시 시도한다. 우선순위는
> 낮음이라 게임과 함께 돌려도 된다.

진행 기록: `sim_preview/solve_all.log`, 서킷별 상태: `assets/racelines/solve_status.json`.

`tools/race_sim.py`는 같은 필드를 화면 없이 끝까지 돌려 추월·접촉·복구·페널티를 센다.
`tools/smoke_gp.py --window`는 실제 게임 루프로 그랑프리를 돌리며 스크린샷과 프레임 시간을 남긴다.

> **반 바퀴 넘는 커팅이 공짜였다.** 진행 거리는 가장 가까운 중심선 샘플의 호 길이 변화를
> ±L/2로 감아서 적분했는데, 인필드를 가로지르면 샘플이 한 스텝에 수 km를 뛴다. 반 바퀴를
> 넘는 점프는 "뒤로 갔다"로 읽혀 이득이 음수 → 5초만. 샘플이 200 m 넘게 뛰면 방향을 짧은
> 쪽이 아니라 차의 이동 방향으로 정하도록 고쳤다(`rules.py`).

## 성능 (`tools/bench_fps.py`)

오토파일럿이 실제로 주행하는 동안 측정. vsync는 Panda 레벨에서 강제 해제.

| Monza | 최적화 전 | **후** |
|---|---|---|
| mean | 70.4 fps (14.64 ms) | **84.6 fps (12.22 ms)** |
| median | 73.7 | **87.6** |
| 1% low | 39.0 | **47.2** |
| 16.7 ms 초과 | 13.2 % | **7.7 %** |

1920×1080에서도 79.2 fps — **CPU 바운드**라 해상도가 거의 무관함(Spa도 동일). 병목은
픽셀이 아니라 프레임당 파이썬·드로우콜.

### 무엇이 비쌌나

| | 비용 |
|---|---|
| HUD 래스터 | 2.4 ms |
| HUD 노드 유지·갱신 | 1.1 ms |
| 노을 셰이더 | 1.6 ms |
| 그림자 | 0.8 ms |

조명이 아니라 **HUD가 제일 비쌌음**. 셋을 고침:

1. **셰이더 유니폼을 엔티티마다 쓰고 있었음** — 프레임당 `set_shader_input` **117회**.
   Ursina는 `continuous_input`을 엔티티마다 루프로 적용하고, `follow()`도 조명받는 엔티티
   전부(차 바퀴·허브 포함)에 썼음. Panda는 셰이더 입력을 씬 그래프로 **상속**하므로
   `scene`에 한 번만 → 프레임당 2회. `Game.update()` 5.21 → 4.49 ms, Panda 상태 GC 절반.
2. **커브 세그먼트 16개를 메시 1개로.** TrackScene 엔티티 22 → 7.
3. **HUD 정적 판 18개를 메시 1개로** (`_QuadBatch`, z를 정점에 구워 깊이 순서 보존).
   HUD 엔티티 61 → 43.
4. 미니맵 아웃라인을 1160점 → 180점. 0.3 크기 위젯에 1/5픽셀당 선분은 낭비.

### 측정이 두 번 틀렸던 기록

> **① 빈 창도 21 fps였음.** 무엇을 끄든 47 ms에 고정돼서 부하가 아니라 상한이라고 보고
> **아무것도 없는 Ursina 창**을 재봤더니 똑같았음. 원인: **Ursina의 `vsync=False`가 Panda에
> 전달되지 않음** — `sync-video`가 계속 true. 창 생성 전에
> `loadPrcFileData('', 'sync-video 0')`를 넣으니 빈 창 974 fps.
> **그 전 수치는 전부 무의미했고, 그대로 답했다면 "34 fps"라고 잘못 말할 뻔했음.**
>
> **② 프레임 수를 바꿔가며 비교했음.** 900 vs 600 프레임은 랩의 **다른 구간**을 재는 것이라
> "unlit이 더 느리다" 같은 말이 안 되는 결과가 나왔음. 같은 조건 3회 반복(33.7/33.8/34.6)으로
> 재현성부터 확인한 뒤에야 비교가 가능해짐.

파이썬 GC는 스파이크의 원인이 **아니었음**(`gc.freeze()+disable()`로 1% low 45.6 → 47.1,
오차 범위). 남은 1% low 21 ms의 원인은 특정하지 못함.

게임 본체는 `vsync=True`로 도므로 실사용은 모니터 주사율에 물림. 60 Hz에서 7.7%의
프레임이 예산을 넘음(개선 전 13.2%).

## 코너링 시 흔들림

카메라 롤과 차체 롤 둘 다 연출용으로 과했음. 방향키를 건드릴 때마다 화면이 흔들리는
느낌이라 낮춤 (`CAM_LEAN`, `BODY_ROLL_GAIN`, `BODY_ROLL_MAX` — 리터럴로 묻어두지 않고
config로 뺌).

| 풀락 유지 | 카메라 롤 이전 → 이후 | 차체 롤 이전 → 이후 |
|---|---|---|

| 120 km/h | 4.44° → **2.66°** | 7.00° → **4.50°** |
| 200 km/h | 5.76° → **3.45°** | 7.00° → **4.50°** |

**한 번 더 낮췄다(차체 자세 전반).** 급가속·급조향에서 움직임이 과해 **윙이 노면 아래로
살짝 파고드는** 게 보였기 때문이다. 원인은 모델 자체에 있다 — 차의 최저점이 y = 0, 즉
지면에 딱 붙어 있어서 **기울기 1도, 스쿼트 1 mm가 전부 노면 아래로 들어간다**.

| | 이전 | 현재 | 최악의 경우 노면 아래로 |
|---|---|---|---|
| `BODY_ROLL_MAX` | 4.5° | **3.2°** | 9.5 cm → **6.8 cm** (1.21 m 바깥) |
| `BODY_PITCH_MAX` | 3.5° | **2.0°** | 13.1 cm → **7.5 cm** (프런트윙) |
| `BODY_SQUAT_MAX` | 7 cm | **3 cm** | 그대로 7 cm → **3 cm** |

피치·스쿼트도 car.py에 리터럴로 박혀 있던 걸 config로 뺐다. 더 줄이려면 이 셋을 낮추면
되고, **완전히 없애려면** 각도를 더 깎거나 기울인 만큼 차체를 들어올려야 하는데 후자는
브레이킹에서 차가 떠오르는 모양이 된다.

## 타이어 — Pacejka Magic Formula

```
F = D sin(C atan(B a - E (B a - atan(B a))))
```

이전엔 선형 + 클램프였음: 그립 한계까지 직선으로 올라간 뒤 **영원히 평평**. 한계를
넘어도 잃는 게 없으니 슬라이드에 고유한 감각이 없었음. 실제 타이어는 피크를 지나면
힘을 **돌려줌** — 그게 한계를 찾을 수 있게 하고 미끄러짐을 숫자가 아니라 감각으로 만듦.

`B`는 피크가 **정확히 `mu / CORNER_STIFFNESS`** — 즉 기존 모델의 피크와 같은 위치에
오도록 유도함. 덕분에 피크를 기준으로 계산하던 모든 식(`steer_limit`, 조향 어시스트,
오토파일럿)이 그대로 유효하고 **곡선의 모양만** 바뀜.

| 슬립각 | Pacejka | 이전(선형) |
|---|---|---|
| 2° | **48%** of peak | 19% |
| 6° | 93% | 57% |
| 10.6° | 100% (peak) | 100% |
| 20° | **95%** | 100% (평평) |
| 45° | **86%** | 100% (평평) |

효과 — 중심 근처에서 힘이 훨씬 빨리 붙어 응답이 빨라지고, 피크 이후 힘이 빠져 한계가
느껴짐:

| | 이전 | 지금 |
|---|---|---|
| 턴인 0.10초 요레이트 | 5.3 °/s | **11.6 °/s** |
| 턴인 0.25초 | 24.1 °/s | **32.1 °/s** |
| 코너링 g (280 km/h) | 2.63 | **2.76** |
| 한계 시 프론트 슬립 | 11.1° | **7.9°** |
| 오토파일럿 최대 이탈 (Silverstone) | 3.9 m | **1.1 m** |

라이선스 메모: Pacejka 식은 출판된 수학이라 GPL 시뮬레이터에서 코드를 가져올 때의
라이선스 부담이 없음.

**참고로 — "GT3 키보드 물리 엔진" 오픈소스는 존재하지 않음.** Speed Dreams·VDrift·
TORCS는 전부 GPL이고 휠+페달 전제로 **보조장치를 의도적으로 안 넣음**. 키보드 조작성은
이 프로젝트가 따로 만든 층(입력 rate 제한, 물리 유도 조향 한계, TC/ABS/ESC/조향
어시스트)이고, 그 엔진들을 가져와도 이 층은 다시 만들어야 함.

**이전 버전과 달라진 점**

기존은 *kinematic* 자전거 모델이었음 — 조향각을 넣으면 요각이 **즉시** 바뀜.
그래서 (a) 좌우 감도가 과도하고 (b) 그립이라는 개념 자체가 없었음.

지금은 *dynamic* 모델:

- **슬립각 → 타이어 횡력 → 요토크 → 요관성** 순서. 방향 전환에 시간이 걸리고,
  한계를 넘으면 언더스티어·슬라이드가 남
- **하중 이동**: 가감속이 앞뒤 축 하중을 바꾸고, 그게 그립을 바꿈
- **다운포스** `F = 2.6·v²` — 고속에서 접지, 저속에서 미끄러움 (레이싱카 특성)
- **마찰원 (combined slip)**: 타이어 마찰 예산은 하나. 풀브레이킹 중엔 못 돌고,
  코너 중 풀스로틀이면 밖으로 밀림
- **파워 제한 엔진** `F = min(F_max, P/v)` — 속도가 오를수록 가속이 줄어듦
- **트랙션 컨트롤** (아래) — GT3 실차와 동일하게 기본 on, `T`로 끌 수 있음

### 트랙션 컨트롤 — 저속 스핀의 원인과 해결

575마력 후륜구동 + 마찰원 조합의 필연적 결과였음. 측정해보니:

```
       엔진력    리어 그립 한계   사용률   남은 횡그립
20 km/h  9038 N      9038 N       99.5%      10.0%   ← 스핀
40 km/h  9279 N      9279 N       99.5%      10.0%   ← 스핀
80 km/h 10213 N     10213 N       99.5%      10.0%   ← 스핀
```

엔진력이 리어 트랙션 한계에 **정확히** 걸려서, 마찰원상 횡그립이 10%만 남음.
100 km/h 이하에서 조향하는 순간 스핀, 복구 불가 (0.9초 만에 스핀).

수정: 마찰원을 뒤집어 **코너링에 안 쓰고 남는 만큼만** 가속에 배분.

```
F_long_max = √((μ·Fz)² − F_lat²)
```

직진 중엔 `F_lat ≈ 0`이라 런치 그립 100% 사용, 코너 중엔 자동으로 줄어듦.
여기에 리어 슬립각이 커지면 추가로 파워를 컷 (실차 TC와 동일).

| | 이전 | 지금 |
|---|---|---|
| 20~150 km/h 풀스로틀+풀조향 | 전부 스핀 | 스핀 없음, 사이드슬립 5~10° |
| 슬라이드 후 복구 | 불가 | 0.41초 |
| 60 km/h 코너 반경 | 21.5 m | **15.7 m** (그립이 남아 더 잘 돌아감) |
| 0-100 | 3.57 s | 4.00 s (TC 대가, 실차도 비슷) |

저속 구간(0.8~6 m/s)은 kinematic↔dynamic 모델을 **블렌딩** — 이전엔 하드 스위치라
경계에서 튀었음.

### ABS — 감속 중 조향이 안 되던 원인

TC와 정확히 대칭인 문제였음. 풀브레이킹하면 프론트 축 마찰 예산을 전부 써버려서
횡그립이 ~10%만 남고, **감속 중엔 아예 안 돌았음**. 마찰원을 뒤집어 프론트/리어 각각
`F_long_max = √((μ·Fz)² − F_lat²)`로 제한:

| 풀브레이킹 + 풀조향 | 이전 | 지금 |
|---|---|---|
| 60 km/h 선회 반경 | 사실상 불가 | **4.2 m** |
| 120 km/h | 불가 | **26.7 m** |
| 200 km/h | 불가 | **76.0 m** |

대가로 300→100 km/h 제동거리가 123 m → 145 m로 늘었는데, ABS의 실제 특성이라 타당한 교환.

**바닥값(`ABS_MIN_SHARE`)이 상한만큼 중요함.** 처음엔 "횡력 쓰고 남은 만큼"만 제동에
줬는데, 타이어가 코너링 한계에 가까워지면 그 값이 **정확히 0**이 됨. 그래서 코너 진입에서
브레이크를 밟고 조향하면 **감속이 아예 멈추고** 속도를 실은 채 밖으로 밀려남 —
운전석에서는 "핸들을 돌려도 그쪽으로 안 간다"로 느껴짐. 실제 ABS는 압력을 조절하지
꺼지지 않음. 축 그립의 40%를 제동 하한으로 보장:

| 브레이크 밟고 조향 (160 km/h 진입) | 이전 | 지금 |
|---|---|---|
| 프론트 제동력 최저 | **0 N** (완전 차단) | 3,950 N |
| 0.83초간 방향 변화 | — | 23.8° |
| 동시 감속 | 없음 | 1.0~1.6 g |

### 조향 어시스트 + 언더스티어 밸런스 — "꾹 누르면 미끄러짐"

두 가지가 겹쳐 있었음.

1. **조향 여유가 과했음** (`STEER_LIMIT_MARGIN` 1.35). 키보드는 항상 100% 입력이라
   프론트가 상시 그립 피크를 35% 넘어가 있었음 → 1.12로 낮추고, 프론트 슬립이 피크를
   넘으면 조향각을 되돌리는 **어시스트** 추가.
2. **더 근본적인 문제 — 앞뒤 밸런스가 정확히 중립이었음.** 자전거 모델에서 앞뒤 μ가
   같으면 언더/오버스티어 경계에 정확히 걸려서 조금만 자극해도 미끄러짐. 실제 GT 차가
   리어 타이어를 더 넓게 쓰는 이유와 같음 → 리어 코너링 강성 7.0 → 8.0,
   리어 그립 6% 상향.

| 풀락 유지 시 최대 차체 사이드슬립 | 이전 | 지금 |
|---|---|---|
| 60 km/h | 7.9° | **6.5°** |
| 120 km/h | 10.6° | **9.4°** |
| 200 km/h | 11.5° | **10.2°** |

슬라이드 복구 0.47초. 0-100은 4.01초 그대로.

### 검증 결과 (`tools/smoke_headless.py`)

```
0-100 km/h 4.01 s · 0-200 km/h 8.41 s · 최고속 279 km/h
300→100 km/h 2.37 s / 123 m (2.0 g)
코너링:  60 km/h 1.45 g │ 120 km/h 1.64 g │ 200 km/h 2.15 g │ 280 km/h 2.40 g
```

GT3 클래스 실차와 부합하는 수치. 오토파일럿이 5개 서킷 전부 트랙 안에서 완주:

| 서킷 | 오토파일럿 | 실제 GT3 |
|---|---|---|
| Monza | 141.7 s | ~107 s |
| Spa | 183.6 s | ~137 s |
| Silverstone | 169.1 s | ~118 s |
| Zandvoort | 135.7 s | ~96 s |
| Catalunya | 148.4 s | ~104 s |

(오토파일럿은 중심선 추종이라 레이싱라인을 안 씀 → 30~40% 느린 게 정상)

### 조향 감도 — 물리로 유도한 제한

핵심 수정. 이전엔 속도에 따라 임의의 곡선으로 락을 줄였는데, 지금은
정상상태 코너링 관계식에서 **직접 계산**:

```
δ = L/R + (α_f − α_r)      ← 원호를 따라가는 각 + 타이어가 힘을 내려면 필요한 슬립
```

`a_lat = μ(W + 다운포스)/m` 을 대입하면 "이 속도에서 앞타이어가 실제로 쓸 수 있는
최대 각"이 나옴. 풀입력이 딱 그 각(×1.35 여유)에 대응하도록 매핑.

- 이전: 200 km/h에서 풀입력 = 그립 한계의 **13배** → 입력 앞부분 몇 %가 전부, 나머지는 스크럽
- 지금: 풀입력 ≈ 한계. 입력 전 구간이 의미를 가짐
- 0.5초 시점 요레이트 **58 °/s → 41 °/s**, 그중 실제 사용 가능 영역은 훨씬 넓어짐

여기에 키보드 입력 rate limit(`STEER_INPUT_RATE`)을 걸어 탭이 스냅으로 안 변하게 함.

### 스티어링 응답 개선

락이 물리로 제한된 뒤로는 입력 rate를 낮게 둘 이유가 없어짐 — 풀입력이 그립 최적각을
넘지 않으므로 빨라져도 민감해지지 않음. 측정해보니 **rate 2.0이 유일한 지연 요인**이었고
(휠 각도가 스틱을 정확히 선형 추종, 랙 298 °/s는 근처도 안 감), 5.0으로 올림.

동시에 **코너링 강성을 슬릭 수준으로** 상향(6.4/8.0 → 8.4/10.2). 강성이 높으면 같은
횡력을 더 작은 슬립각에서 내므로 **응답이 빨라지는 동시에 덜 미끄러짐** — 둘을 맞바꾸는
게 아니라 같이 좋아짐.

| 200 km/h 턴인 | 이전 | 지금 |
|---|---|---|
| 0.10초 요레이트 | 3.3 °/s | **8.1 °/s** |
| 0.25초 요레이트 | 15.6 °/s | **34.5 °/s** |
| 최대치의 90% 도달 | 0.53 s | **0.31 s** |
| 풀락 유지 시 사이드슬립 (150 km/h) | 9.8° | **7.4°** |
| 슬라이드 복구 | 0.50 s | **0.28 s** |

### 조향 어시스트가 수정 입력을 방해하던 문제

어시스트가 **프론트 슬립각 총량**을 기준으로 작동했는데, 차가 미끄러지는 동안은
조향과 무관하게 슬립이 큼. 그래서 카운터스티어(미끄러짐을 잡는 입력)를 넣으면
어시스트가 그걸 **깎아버렸음** — 핸들이 -4.94° ↔ -5.69° 사이로 톱질하고 미끄러짐이
안 끝남. 사용자가 말한 "인풋을 넣어도 반응이 없는 느낌"이 이거였음.

수정: 지금 조향이 슬립을 **줄이고 있으면**(= 수정 중이면) 어시스트가 빠짐.
직진 상태 슬립(`slip + steer`)과 현재 슬립을 비교해서 판단함.

### ESC (자세 제어) 추가

조향이 요청하지 않은 요(yaw)를 감쇠시킴. 없으면 카운터를 유지해도 반대쪽 정상 슬라이드로
바뀔 뿐 **미끄러짐이 끝날 이유가 없음**. 오버스티어만 잡고 언더스티어는 건드리지 않음 —
타이어가 못 내는 요를 만들어내면 거짓이니까. HUD에 `ESC` 표시.

미끄러짐 정착: 80/120/160 km/h 전부 **0.4초**.

### 고속 입력 완화 — 평탄하다 급격히 떨어지는 곡선

같은 키 입력이 저속에선 빠른 플릭, 고속에선 섬세한 조작이 되도록 낮추되, **선형이 아니라
무릎(knee) 이후 smoothstep**으로 떨어뜨림. 선형은 첫 km/h부터 깎기 시작해서 아직
날카로워야 할 100 km/h에서 이미 둔해지고, 정작 필요한 고속에서는 남은 게 없음.

속도에 따라 움직이는 두 가지가 **같은 곡선 모양**을 공유함:

| | 무릎 | 완전 적용 | 크기 |
|---|---|---|---|
| 입력 rate (`STEER_RATE_*`) | 130 km/h | 290 km/h | −64% |
| 조향각 여유 (`STEER_MARGIN_*`) | 130 km/h | 230 km/h | +0.30 |

**조향각 제한** (`steer_limit`) 변화 — 130까지 평탄하게 +26%, 230에서 기존값으로 수렴:

| km/h | 60 | 100 | 130 | 160 | 180 | 200 | 230 | 260 |
|---|---|---|---|---|---|---|---|---|
| 이전 | 15.8° | 8.7° | 7.4° | 7.0° | 7.0° | 7.0° | 7.2° | 7.4° |
| 이후 | 20.0° | 11.0° | 9.3° | 8.5° | 7.9° | 7.4° | 7.2° | 7.4° |
| | +27% | +26% | +26% | +21% | +13% | +6% | ±0% | ±0% |

**여유를 줘도 공짜인 이유**: 최적 조향각은 좁은 점이 아니라 **넓은 플래토**임 —
100 km/h에서 6°/8°/10°가 각각 43.4 / 44.3 / 44.2 °/s. 게다가 조향 어시스트가 최적점으로
다듬어 주므로 여유분은 헤드룸으로만 작동함. 실제로 정상상태 선회율이 **+1.5% 개선**됨.

**키를 누르고 0.5초 뒤 실제로 돌아간 각도**(rate·제한·응답 전부 포함):

| km/h | 60 | 100 | 130 | 160 | 200 | 230 | 260 | 290 |
|---|---|---|---|---|---|---|---|---|
| 이전 | 25.0° | 19.3° | 17.5° | 16.5° | 15.6° | 15.0° | 14.6° | 14.4° |
| 이후 | 26.2° | 21.5° | 19.6° | 18.2° | 16.3° | 15.1° | 14.0° | 13.4° |
| | +5% | +12% | +12% | +11% | +5% | **±0%** | −4% | −6% |

> **못 하는 것**: 130 km/h까지 "차이 없게"는 물리적으로 불가능함. 선회율 = 횡가속도 ÷ 속도라,
> 60 km/h의 선회율을 130 km/h에서 내려면 **4.18 g**가 필요한데 가진 건 약 2.3 g.
> 60→130 낙폭을 100→70%에서 100→75%로 완만하게 만든 게 한계.
>
> 여유(`STEER_MARGIN_LOW_EXTRA`)를 0.30 → 1.20까지 올려봤지만 100~130에서 **+5.6%**만
> 늘고 프론트 슬립이 12.6° → 17.0°로 타이어 피크(13.6°)를 넘어감. 0.30이 턴인 중에도
> 프론트를 피크 안쪽에 유지하는 최대값.

단 **AI·게임패드는 `Controls.analog_steer=True`로 이 필터를 우회** — 이미 아날로그
신호라 두 번 필터링하면 0.5초 지연이 생겨 컨트롤러가 발산함 (실제로 겪은 버그).

### 크게 미끄러질 때 조작이 먹지 않던 문제 — 원인은 제어가 아니라 타이어

위의 어시스트·ESC 수정은 전부 **제어 계층**을 건드렸는데, 진짜 원인은 타이어 모델에
있었음. 저속에서 슬립각이 정의되지 않는 걸 피하려고 0.8~6 m/s 구간에서 타이어 힘을
0부터 키우는 블렌드 `w`가 있는데, 이게 **전진 성분(`v_long`)** 기준이었음.

크게 미끄러지면 빠르게 달리는 중에도 전진 성분은 무너짐. 100 km/h에서 사이드슬립
85°를 강제로 준 뒤 재보니 `v_long = 2.3 m/s` → `w = 0.28`, 즉 **미끄러지는 바로 그
순간에** 모든 타이어 힘이 1/4로 줄어들고 있었음. 그러니 입력도 안 먹고, 미끄러짐을
멈출 힘도 없어서 계속 미끄러짐.

블렌드가 존재하는 이유는 "**속도**가 낮으면 슬립각이 무의미해서"고, 그 속도는 속도
벡터 전체의 성질이지 한 축의 성질이 아님 → 총 속력 기준으로 변경.

| 사이드슬립 85°, 100 km/h | 이전 | 이후 |
|---|---|---|
| 블렌드 `w` | 0.28 | **1.00** |
| 프론트 횡력 | 2213 N | **7798 N** |
| 미끄러지는 동안 감속 | 거의 0 | **0.8~1.3 g** |

카운터스티어 유지 시 복귀: 40° 슬라이드 **0.84초**, 60° **1.39초** (속도도 함께 깎임).

> 진단 함정: 처음엔 "슬라이드 중 조향 → 요 응답" 을 재서 0이 나와 수정이 실패한 줄
> 알았음. **부호를 반대로 줘서 미끄러지는 쪽으로 조향하고 있었던 것.** 입력이 아무
> 효과가 없다고 나오면 먼저 부호 규약을 의심할 것.

### ABS 배분을 상수에서 운전자 입력으로

`ABS_MIN_SHARE`라는 **상수 하나**가 "돌기 vs 멈추기" 배분을 정하고 있었음. 200 km/h에서
브레이크·조향 둘 다 최대로 두고 재보니:

| 설정 | 감속 | 횡 | 1.5초 후 |
|---|---|---|---|
| ABS 끔 | 1.92 g | **0.14 g** | 안 돌아감 (원래 버그) |
| 상수 0.40 | **0.85 g** | 1.75 g | 잘 돌지만 안 멈춤 |
| 상수 0.70 | 1.26 g | 1.35 g | — |

둘 다 말은 되지만 **숫자 하나가 정할 문제가 아님**. 그래서 예약량을 운전자 입력 비율
(`brake / (brake + |steer|)`)에서 뽑도록 바꿈 — 측정된 힘이 아니라 **의도** 기준이고,
마찰원은 그대로 총량을 제한함.

| 브레이크 | 조향 | 감속 | 횡 | 1.5초 후 |
|---|---|---|---|---|
| 1.0 | 0.0 | 1.66 g | 0.00 g | 97 km/h |
| 1.0 | 0.3 | 1.53 g | 0.77 g | 105 km/h |
| 1.0 | 1.0 | 1.06 g | 1.57 g | 126 km/h |
| 0.3 | 1.0 | 0.78 g | 1.85 g | 151 km/h |
| 0.0 | 1.0 | 0.29 g | 2.13 g | 178 km/h |

직선 제동은 **완전히 불변**(300→100 km/h 145.3 m, 2.44 g) — 조향이 0이면 예약이
걸릴 일이 없으므로 당연한 결과.

> 이전에 제가 "`ABS_MIN_SHARE` 때문에 직선 제동이 2.0 → 1.7 g로 떨어졌다"고 적어둔 건
> **틀렸음**. `max(spare, floor)`는 허용치를 올리기만 하므로 직선 제동을 깎을 수가 없음.
> 실제 원인은 스모크 테스트가 (a) 직전 가속 테스트의 차를 이어받아 279 km/h에서
> 제동했고 (b) "peak"라고 찍던 값이 사실 **마지막 스텝**의 순간 감속(=100 km/h, 다운포스
> 거의 없음)이었던 것. 둘 다 수정함.

### 저속 최대 조향 확대

`MAX_STEER` 30° → **42°**, `STEER_LIMIT_FREE_SPEED` 7 → **10 m/s**.

| 속도 | 10 | 20 | 30 | 36 km/h |
|---|---|---|---|---|
| 조향각 | 42° | 42° | 42° | 28.6° |
| 회전반경 | 3.4 m | 3.7 m | 6.9 m | 7.8 m |

10 km/h 회전 지름 6.9 m — 실제 GT3(약 11~12 m)보다 작음. **의도한 것**: 축전에서
관람객이 스핀했을 때 몇 번씩 왔다갔다 하지 않고 바로 방향을 잡을 수 있어야 함.
임계속도 위로는 물리 기반 `steer_limit`이 그대로 지배하므로 주행 속도 영역은 불변.

## 깊이(Z) 정밀도 — 반복되던 렌더링 오류의 진짜 원인

흰 선이 멀리서 사라지고, 그림자가 차체를 덮고, 부품이 서로 뚫고 보이던 문제들은
전부 **하나의 근본 원인**에서 나왔음. depth offset으로 계속 땜질했는데 그게 잘못이었음.

24비트 깊이 버퍼의 정밀도는 **near 평면이 지배**함. 거리 d에서 구분 가능한 최소 간격은
대략 `d² / (near × 2²⁴)`. Ursina 기본값은 **near 0.1 / far 10000**:

| 거리 | 기본값(near 0.1) 구분 한계 | 수정 후(near 1.5) |
|---|---|---|
| 100 m | 5.96 mm | **0.40 mm** |
| 300 m | 53.6 mm | **3.6 mm** |
| 800 m | 381 mm | **25 mm** |

도로 마킹은 아스팔트보다 15 mm 높은데, 300 m에서 54 mm를 못 가리니 **당연히 사라졌음**.
depth offset 스택은 전부 이 정밀도 부족을 가리려던 보상이었고, offset 자체가 상수
NDC 시프트라 가까운 거리에서는 과도하게 작용해서 (그림자가 차를 덮는 등) 새 버그를 만듦.

**수정**: `CLIP_NEAR = 1.5`, `CLIP_FAR = 1200`. near를 15배 올려 전 구간 정밀도 15배 개선.
그 결과 **depth offset을 전부 제거**하고 실제 높이 차이만으로 레이어링:

```
잔디 -0.05 < 아스팔트 0 < 이음매 0.020 < 커브 0.025 < 흰선 0.035 < 출발선 0.045 < 그림자 0.060 < 차 0.10+
```

모든 간격이 10 mm 이상이라 ~600 m까지 안정적으로 해상되고, 그 너머는 안개가 가림.
보닛 카메라는 차 안에 있어서 near 평면에 잘리므로 그 모드에선 차를 숨김(레이싱 게임 관행).

카메라 순서는 `CAM_MODES = ("onboard", "chase", "far")` — 좁은 시점부터 바깥으로 나가는
순서다. 다만 **세션이 시작되는 시점은 `CAM_DEFAULT`("chase")**: 처음 달리는 서킷에서 차를
놓을 수 있는 건 체이스이고, 온보드는 코스를 익힌 뒤 바꿔 타는 시점이다. 보닛 시점은
만들어져 있지만 순환에서 빼 뒀다(`CAM_MODES`에 `"hood"`를 도로 넣으면 그대로 돌아온다).

> **체이스 거리는 화면에서 역산했다.** 원하는 구도가 프리캠 스크린샷으로 왔는데, 프리캠은
> FOV를 건드리지 않아서 그 값이 F를 누른 순간의 주행 FOV로 얼어 있었다. 같은 차 크기(화면
> 폭의 17%)라도 FOV 60°면 12.4 m, 87°면 7.6 m라 거리가 하나로 정해지지 않는다. 주행 중
### 정지와 주행의 구도 차이 (프레임 고정)

속도가 붙으면 FOV가 열리고(정지 60° → 80 km/h 74° → 300 km/h 130°대) **주행 중 시선
거리(lead)도 길어진다**. 오프셋이 고정이면 이 둘 때문에 같은 카메라가 정지와 주행에서
전혀 다른 구도를 만든다 — 정지에서 차가 크게 부풀고 화면 아래로 내려가 텔레메트리 위젯에
가렸다. 두 가지로 상쇄한다.

1. **크기**: FOV가 열린 비율(`tan` 비)만큼 체이스 오프셋 전체를 뒤로/위로 늘린다
   (`CAM_FRAME_REF_FOV`=70°, `CAM_FRAME_LOCK`=1.0, `CAM_FRAME_SCALE` 클램프). 오프셋
   **전체**를 스케일하므로 차를 보는 각도는 유지된 채 크기만 고정된다.
2. **위치**: 정지에서 짧아진 lead가 시선을 들어올리는 만큼 조준 높이를 낮춘다
   (`CAM_CHASE_AIM_LOW` 0.85 m → `CAM_CHASE_AIM_SPEED`(22 m/s)에서 1.35 m).

Monza 실측(차 폭 = 화면 폭 대비 %, 지붕 = 화면 위에서 %):

| | 적용 전 정지 | 적용 후 정지 | 80 km/h(기준) |
|---|---|---|---|
| 차 크기 | 23.6% | 19.2% | 15.3% |
| 지붕 위치 | 79.7% | 73.1% | 66.5% |

즉 크기 차이 1.65배 → 1.25배, 위치 차이 13.1 → 6.6 포인트로 절반이 됐고, 80 km/h 구도
자체는 그대로다(지붕 66.6% → 66.5%). 남은 차이는 **가속 중 카메라 지연**(`CAM_MAX_LAG`
2.2 m) 때문인데, 이건 가속감을 내려고 일부러 넣은 것이라 그대로 뒀다 — 지연을 끄고 재면
정지 19.3% vs 80 km/h 19.2%로 크기가 정확히 일치한다.

> FOV(~87°)를 기준으로 맞춰 7.5 m / 높이 2.7 m로 잡았고, 141 km/h로 달리며 렌더한 컷의 차
> 크기가 참고 화면과 같은 17%로 나왔다. 이후 요청에 따라 조금 더 붙이고 올려 **6.3 m /
> 높이 3.4 m** — 차를 위에서 내려다보는 각이 되어 코너에서 노면이 정면으로 보인다.

**온보드(T-cam)는 반대 문제였다.** 차 위에 붙어 있으니 차가 보여야 하는데, near = 1.5 m가
헤일로·에어박스·노즈를 통째로 잘라내서 텅 빈 도로 위에 프런트윙만 떠 있었다. 이 모드에서만
near를 `CLIP_NEAR_ONBOARD`로 낮춘다. 시선도 장착 높이가 아니라 `CAM_ONBOARD_AIM_Y`(0.68 m)를
겨냥해 살짝 아래를 봐야 노즈가 화면 아래를 채운다.

**그 다음은 고속에서 차체가 near 평면에 잘리는 문제였다.** 단일 패스 렌더러에 "클립 금지"
설정 같은 건 없다 — near 평면은 언제나 뭔가를 자른다. 선택지는 셋뿐이고(① near를 더 낮춰
원거리 정밀도를 내주거나 ② 차체가 near 안에 절대 못 들어오게 띄우거나 ③ 차만 별도 패스로
나중에 그리거나), 여기서는 ②를 기본으로 ①을 조금 섞었다.

- 카메라 높이 **1.40 m**, 차의 최고점(에어박스 0.98 m) 위로 **0.42 m 여유**.
- `CLIP_NEAR_ONBOARD` = **0.35 m** — 여유 안쪽이라 차체는 near 평면 바깥에 머문다.
- 남는 마진(7 cm)보다 셰이크가 크다(300 km/h ±5.5 cm, 오프트랙 17.6 cm). 에어박스가
  찢어지던 게 정확히 이 조합이라, **이 시점에서만 셰이크의 아래 방향 성분을 없앤다**
  (`dy = abs(dy)`). 옆·앞뒤·위로는 그대로 흔들리므로 화면 느낌은 같고, 카메라 아래 여유는
  줄어들 수가 없다. 셰이크를 통째로 끄는 것보다 이쪽이 낫다 — 흔들림은 이 시점의 일부다.

정밀도 비용은 300 m에서 약 15 mm(0.6 m일 때는 9 mm)이고, 그 카메라를 쓰는 동안에만 낸다.
카메라를 더 낮추고 싶으면 `높이 − 0.98 m ≥ CLIP_NEAR_ONBOARD`만 지키면 된다.

**온보드에는 FOV 하한(`CAM_ONBOARD_FOV_MIN` 88°)이 있다.** 기본 FOV는 정지에서 60°인데,
그 화각으로는 노즈가 화면 아래로 빠져나가 **정지 상태에서 차가 아예 안 보였다** — 속도가
붙어 FOV가 열려야 비로소 차가 나타났다. 실제 온보드 카메라도 어느 속도에서나 광각이다.

**체이스는 속도가 붙으면 올라간다**(`CAM_CHASE_RISE` 0.6 m, `CAM_CHASE_RISE_FROM` 22 m/s
부터). 위의 프레임 고정이 오프셋 전체를 스케일하다 보니 270 km/h에서 카메라가 80 km/h보다
1 m 낮게 앉아 앞쪽 시야가 눌렸다. 기준 속도부터 올라가게 해서 빠를수록 트랙 앞이 더 보이게
하고, 기준 속도 이하에서는 튜닝해 둔 구도를 건드리지 않는다. 처음엔 2.0 m였는데 카메라가
차에서 떠오르는 것처럼 보여서 0.6 m로 낮췄다 — 200 km/h에서 +0.31 m, 최고 속도에서 +0.6 m.

32비트 깊이 버퍼도 요청해봤지만 드라이버가 24비트만 줌 — near 평면이 유일한 레버였음.

## 자동차 모델 — 기성 CC0 에셋 + 검증된 로더

직접 만든 절차적 차체는 버리고 **Kenney Racing Kit**(CC0)의 레이스카를 씀.
로딩도 손으로 짠 파서가 아니라 Ursina에 이미 들어있는 **`panda3d-gltf`**를 사용.

```
assets/models/kenney/     커밋된 에셋 (레이스카 4색 + 트랙 소품), LICENSE.txt 동봉
assets/vendor/            원본 zip (gitignore)
```

라이선스는 **CC0 1.0** — 출처 표기 의무 없고 상업적 사용 가능. 축전용으로 안전함.
(표기는 선택이지만 안내판에 Kenney 한 줄 넣어주면 좋음)

### 왜 바꿨나

절차적으로 만든 차체는 구멍·부품 관통·재질 손실 같은 문제가 계속 재발했고, 매번
검사 스크립트를 새로 짜서 잡아야 했음. 기성 에셋은 **제작자가 이미 검증한 형상**이라
그 문제군 자체가 사라짐. 로더도 마찬가지 — glTF 재질·법선·노드 계층을 검증된
구현이 처리함.

### 이 코드가 여전히 하는 일

게임 고유의 부분만 남음:

- **휠베이스에 맞춰 스케일** — 에셋의 축간거리를 읽어서 물리 휠베이스에 맞춤.
  숫자를 하드코딩하지 않아서 다른 차 모델로 바꿔도 바퀴가 맞음
- **바퀴 리깅** — `wheelFrontLeft` 등 이름으로 노드를 찾아 조향/회전 허브에 매닮
- **텔레메트리 구동** — 실제 횡가속으로 롤, 종가속으로 피치, 실제 조향각·속도로 바퀴

### 이 과정에서 밟은 함정 3개

1. **Ursina의 `model=`은 절대경로를 못 씀** (에셋 폴더 안 이름만 찾음)
   → `base.loader.loadModel(Filename)`로 직접 로드
2. **Ursina Entity가 흰색 ColorAttrib를 검** — Panda에서 ColorAttrib는 재질을
   *덮어씀*(틴트가 아님). 차가 통째로 흰색으로 나온 이유. glTF 재질의 baseColor를
   geom 상태에 flat color로 구워넣어 해결 (게임의 나머지 플랫셰이딩과도 일관됨)
3. **바퀴가 날아감** — 허브를 바퀴의 *저작 피벗*에 놨는데, 그 좌표는 에셋 내부
   부모 기준이라 body 공간과 달랐음. 스핀 회전이 바퀴를 호를 그리며 날려버림.
   → `get_tight_bounds(self.body)`로 **body 공간에서의 바퀴 중심**을 구해 허브를 놓음

## 프레임 부드러움

물리는 고정 스텝(120 Hz), 렌더는 가변 프레임이라 한 프레임에 스텝이 2~3회씩
들쭉날쭉 들어감 → 60 fps가 나와도 **차가 매 프레임 다른 거리만큼 튐**.

- **렌더 보간** — 마지막 두 물리 상태 사이를 `alpha = accum/DT`로 보간해서 그림.
  카메라도 **같은 보간 포즈**를 써야 함 (안 그러면 도로 튐)
- **HUD 텍스트 캐싱** — Ursina는 `Text.text` 대입마다 글리프 메시를 다시 만듦.
  값이 안 바뀐 프레임엔 건너뜀 → 1.98 ms → 0.80 ms

  한 스텝에 차가 1샘플도 못 가므로 ±10으로 축소 (경계에 걸리면 전체 스캔으로 폴백)

## HUD / 미니맵

미니맵은 점 두 개뿐 — **파란 점 = 출발·결승선, 빨간 점 = 내 차**.

전체화면에서 이 표시가 트랙 밖으로 나가던 건 진짜 버그였음. Ursina는 종횡비가 바뀌면
`camera.ui`의 **직속 자식마다** `e.x`를 다시 스케일함(`window.update_aspect_ratio`).
미니맵 폴리라인은 엔티티 x가 0이라 안 움직였는데, 출발선 마커는 x가 0.5574여서
1.937/1.778배 되어 0.6075로 밀려남 — 정확히 관측된 값.

→ 미니맵 구성요소를 **컨테이너 엔티티 하나** 안에 넣어, 직속 자식은 컨테이너뿐이 되게 함.
1.778 → 1.333으로 바꿔 검증: 컨테이너는 0.62 → 0.465로 이동(비율 유지), 내부 요소들의
로컬 좌표는 불변, 차 마커는 외곽선에서 0.09 px. 페달·슬립 표시도 같은 이유로 컨테이너화.

## 레이스 AI의 학습 판단 층 (강화학습)

그랑프리의 AI는 "풀이 찾은 최적 라인을 추종하는 층(`mintime_driver`) + 그 위에서 0.1초마다
어느 차선으로 얼마나 밀지 정하는 규칙 층(`racecraft`)"이다. 추월·수비·합류가 사람답지 않은 건 이
규칙 층이므로 **그 층만** 학습된 정책으로 바꾼다. 라인 추종, 회피 안전망(room·leader cap), 황기,
복구는 그대로 규칙이 맡는다. `game/config.py`의 `RACE_AI`가 `"rl"`(기본)이면
`assets/policies/raceai.npz`(112 KB, numpy만으로 추론)를 쓰고, 파일이 없거나 `"rules"`이면 예전의 규칙이 결정한다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 환경·장면 생성기·심판 지표·규칙 AI 기준선 | 완료 |
| 2 | 규칙 층을 따라 하는 모방 학습(BC) | 완료 (`policy/raceai/bc.npz`) |
| 3 | 장면 RL (추월·수비·병합·밀집·출발), Kaggle CPU | 완료 (4시간 × 2회 실행) |
| 4 | 복구·합류, 20대 레이스 검증 | 복구는 규칙 유지, 출발 장면을 학습에 추가, 전체 레이스로 검증 |
| 5 | 게임 통합 (`RaceDriver.policy`, 규칙 폴백) | 완료 |

**파일**: `game/raceai.py`(관측 60차원 + 행동 24개, numpy 추론), `game/raceenv.py`(장면·심판·`RaceEnv`),
`tools/race_metrics.py`(지표), `tools/raceai_collect.py`(규칙의 결정 기록), `tools/train_raceai.py`(모방 학습),
`tools/ppo_raceai.py`(PPO), `tools/smoke_raceai.py`(배관 점검), `../ai_sw_gpu/kaggle/raceai_push.py`(Kaggle 학습 커널 업로드).
`RaceDriver.policy`가 설정되면 규칙 `_plan`/`_attack_lane` 대신 그 정책이 plan tick마다(약 7.5 Hz)
`raceai.apply_action`으로 차선과 페이스를 정한다 (없으면 이전과 똑같음).

**행동**: 계획 라인에서의 차선 오프셋 7개(−6…+6 m) × 페이스 3개(0.94/1.0/1.03) = 21개와, 규칙의
"안쪽 파고들기"를 그대로 호출하는 옵션 행동 3개(`ATTACK_IN`, `ATTACK_OUT`, `HOLD`). 오프셋만으로는
브레이킹 존 안쪽으로 파고드는 추월을 표현할 수 없어 옵션 행동을 두었다.
**관측**: 내 차선·여유 폭·속도, 앞쪽 20–300 m의 곡률과 계획 속도, 제동까지 거리, 브레이킹 존,
`lane_age`, 가장 가까운 6대(간격·횡위치·접근 속도·정지 여부).

**학습**: 규칙의 결정 26만 쌍으로 BC(검증 정확도 88%)로 초기화한 뒤 PPO(범주형, GAE, 샘플링 온도 T=1.25,
이웃이 없는 곳에서만 BC에 KL 고정)로 학습했다. 장면은 tow/sbs/defend/merge/pack(서킷은 23개 중 Sepang,
Hockenheim, Montreal을 제외한 20개)과 20대가 출발하는 start이고, 보상은 진행·순위·접촉·스튜어드 페널티·
복구·차선 흔들기다. Kaggle CPU 커널(4코어, 4시간)에서 시뮬레이션이 병목이라 GPU는 쓰지 않았다.
교훈: ① 관측은 규칙 판단 *앞*에서 만든다(뒤에 만들면 규칙의 공격 플래그가 새어 정확도 98%인데 닫힌 루프에서는 추월이 사라짐),
② 장면의 난이도 보정이 중요하다(tow는 이기기 어려웠다), ③ 오래 학습할수록 추월 성공률이 내려간다(접촉·페널티를 줄이는 쪽으로
수렴) — 그래서 평가가 가장 높았던 초반 체크포인트(10–40회)를 쓴다.

**결과** (`python tools/race_metrics.py --policy X.npz`, 8개 서킷 × 시드 8 = 장면당 64회, 정책이 ego만 운전):

| 장면 | 규칙 성공 | BC 성공 | **PPO 성공** | 규칙 접촉률 | PPO 접촉률 | 규칙 ego 페널티 | PPO ego 페널티 |
|---|---|---|---|---|---|---|---|
| tow | 0.30 | 0.41 | 0.41 | 0.08 | 0.14 | 0.06 | 0.00 |
| sbs | 0.81 | 0.77 | 0.77 | 0.19 | 0.23 | 0.02 | 0.02 |
| defend | 0.69 | 0.70 | 0.72 | 0.27 | 0.25 | 0.06 | 0.03 |
| merge | 1.00 | 1.00 | 1.00 | 0.00 | 0.00 | 0.00 | 0.00 |
| pack | 0.73 | 0.61 | 0.75 | 0.95 | 0.94 | 0.03 | 0.03 |
| 평균 | 0.706 | 0.697 | **0.728** | | | | |

장면 하나당 64회라 ±0.06 정도의 오차가 있다. 성공률 차이는 오차 안이고, 일관되게 보이는 것은
페널티·복구가 줄어든다는 점이다.

**20대 3랩 레이스 8회**(모든 차가 같은 정책, 같은 서킷·시드):

| | 규칙 | PPO |
|---|---|---|
| 랩당 추월 | 15.0 | 10.0 |
| 레이스당 접촉 | 20.6 | 18.1 |

PPO 쪽이 덜 흔들고(차선 이동 43% 감소), 복구와 페널티가 줄며, 추월 횟수는 3분의 2로 줄어 한결 얌전하다.
한계: 접촉 자체는 크게 줄지 않았고(밀집 pack 장면은 규칙과 같이 거의 항상 접촉), 추월 성공률 향상은 미미하다.
결과 JSON은 `policy/raceai/` (`ppo_kg_*.json`, `races8_*.json`), Kaggle 학습 로그는 `policy/raceai/kg_*/ppo/ppo_log.jsonl`.

**장면** (`raceenv.make_scenario(서킷, 종류, 시드)`): `tow`(느린 차 뒤 슬립스트림, 브레이킹 존 앞 330 m),
`sbs`(브레이킹 존 140 m 앞 나란히), `defend`(더 빠른 차가 14–30 m 뒤), `merge`(도로 가장자리에
선 차 + 접근하는 4대), `pack`(60 m 안에 8대), 학습 전용 `start`(20대 출발). 서킷과 시드만 있으면
같은 장면이 재현된다. 성공 기준: tow/defend = 접촉·페널티 없이 끝에 앞섬, sbs = 접촉·페널티 없음,
merge = 접촉 없이 도로 복귀, pack = 접촉 없음.

**다시 학습하려면**: `python tools/ppo_raceai.py --bc policy/raceai/bc.npz --out policy/raceai/run1 --jobs 4`
(Windows는 작업자 4개까지, 그 이상은 메모리 오류), Kaggle은 `python ../ai_sw_gpu/kaggle/raceai_push.py <이름> --hours 4`.
규칙 AI 기준선: `python tools/race_metrics.py --name baseline_rules` (모든 차를 정책이 몰게 하려면 `--all-cars`, 전체 레이스는 `--races N`).
